Час і частота помилок залежать від CPU та навантаження, тому важливі закономірності, а не точні числа.

**Центральне питання:** що станеться, якщо декілька threads одночасно змінюють одну shared variable?

```
                 Process
                    │
        ┌───────────┼───────────┐
        ▼           ▼           ▼
     Thread 1    Thread 2    Thread 3      ← свої stack і регістри
        └───────────┼───────────┘
                    ▼
        Shared memory (code, data, heap)
```

## Головне за 30 секунд

- **Threads живуть в одному процесі й ділять пам'ять.** Адреса глобальної `value` однакова для обох threads, а стеки в них різні (адреси `local` відрізняються рівно на `0x801000`, тобто 8 МБ + 4 КБ).
- **Порядок threads не гарантований:** у восьми запусках `multiple_threads` було чотири різні порядки.
- **`counter++` не атомарний.** Це три кроки: прочитати, додати 1, записати. Тому два threads по 1 000 000 разів дали, наприклад, `1114953` замість `2000000` (lost update).
- **Гонка проявляється не завжди:** на 1 000 000 ітерацій вона вдалась у 10 запусках зі 100, на 10 000 000 у 20 зі 20. Три-п'ять успішних запусків нічого не доводять.
- **`mutex` виправляє:** 5 з 5 запусків дали `2000000`. Ціна: ~10 разів повільніше (0,1 с проти 0,009 с).
- **Deadlock:** два threads, що беруть два mutex у протилежному порядку, зависають назавжди. Усі threads у стані `futex_wait`, CPU не споживають. Виправлення: однаковий порядок блокувань.
- **`parallel_sum`:** кожен thread рахує свою локальну суму, mutex не потрібен, результат `500000500000` збігається з формулою.

## 1. Перший thread: `first_thread.c`

```
$ ./first_thread
Main: creating thread
Hello from worker thread!
Main: worker finished
```

До `pthread_create` процес мав один thread (main), після — два: main і worker.

**Скільки processes створила програма?** Жодного нового: процес один, змінився лише кількість threads у ньому.
**Скільки threads після успішного `pthread_create()`?** Два (main і worker).
**Яка функція виконується новим thread?** `worker()`, яку ми передали третім аргументом.
**Для чого `pthread_join()`?** Main чекає, доки worker завершиться. Без цього `main` міг би завершитись першим, і разом із ним закінчився б увесь процес разом з усіма threads.
**Чи створює `pthread_create()` новий address space?** Ні. Новий thread працює в адресному просторі того самого процесу. Це головна відмінність від `fork()` із Lab 4.

## 2. Декілька threads: `multiple_threads.c`

Вісім запусків, порядок, у якому threads надрукували повідомлення:

| Run | Порядок |
|---:|---|
| 1 | 1, 4, 2, 3 |
| 2 | 1, 4, 2, 3 |
| 3 | 2, 1, 3, 4 |
| 4 | 4, 1, 2, 3 |
| 5 | 1, 2, 3, 4 |
| 6 | 1, 2, 3, 4 |
| 7 | 1, 2, 3, 4 |
| 8 | 1, 2, 3, 4 |

Ще один запуск повністю:

```
Thread 1 is running
Thread 3 is running
Thread 2 is running
Thread 4 is running
All threads finished
```

**Чи гарантує цикл `pthread_create` порядок 1 → 2 → 3 → 4?** Ні. Цикл лише створює threads у цьому порядку, а коли кожен із них почне виконуватись, вирішує scheduler (планувальник ОС): він сам вибирає, якому thread і на якому ядрі дати процесор. Новий thread може стартувати одразу, а може трохи пізніше, тому порядок виводу змінюється від запуску до запуску. Це nondeterministic execution.

Шість запусків (адреси скорочено до останніх цифр, але в кожному запуску вони повністю однакові для всіх рядків):

| Run | Порядок виведення | Адреса `value` | Main: value |
|---:|---|---|---:|
| 1 | T2, T1 | `0x56282c415014` | 100 |
| 2 | T2, T1 | `0x556f9c02f014` | 100 |
| 3 | T2, T1 | `0x55dfc0ef4014` | 100 |
| 4 | T1, T2 | `0x557e49f13014` | 200 |
| 5 | T1, T2 | `0x555555e4e014` | 200 |
| 6 | T2, T1 | `0x561f3a37c014` | 100 |

Приклад одного запуску:

```
Thread 2: value=200, address=0x56282c415014
Thread 1: value=100, address=0x56282c415014
Main: value=100, address=0x56282c415014
```

```
Thread 1: 0x56282c415014
Thread 2: 0x56282c415014
Main:     0x56282c415014
```

**Чи однакова адреса `value` для threads?** Так, в усіх трьох місцях.
**Чому?** Усі threads одного процесу працюють в одному адресному просторі, тож глобальна змінна одна, і `&value` для всіх означає те саме місце в пам'яті.
**Чому фінальне значення може залежати від порядку?** Обидва threads пишуть у ту саму змінну без синхронізації, тому виграє той, хто записав останнім: у 4 запусках зі 6 вийшло 100 (останнім писав Thread 1), у 2 запусках 200. Між запусками адреса змінюється (ASLR), але всередині запуску вона спільна.

```
Processes (Lab 4)               Threads (Lab 5)

Process A       Process B       Thread A ──┐
value           value                      ├──→ shared value
separate address spaces         Thread B ──┘
```

## 4. Чи має thread власний stack: `thread_stacks.c`

```
$ ./thread_stacks
Thread 2: local=20, address=0x7f0edc3fdeb0
Thread 1: local=10, address=0x7f0edcbfeeb0
```

Ще два запуски: `0x7f38c89fdeb0` / `0x7f38c91feeb0` та `0x7f92fadfdeb0` / `0x7f92fb5feeb0`.

```
Thread 1 local: 0x7f0edcbfeeb0
Thread 2 local: 0x7f0edc3fdeb0
```

У всіх трьох запусках різниця адрес однакова: `0x801000` = 8 388 608 + 4096 байтів = **8 МБ (розмір stack за замовчуванням) + 4 КБ (guard page)**. Тобто кожному thread бібліотека виділила окремий stack розміром 8 МБ.

**Чому `value` була shared, а `local` має різні адреси?** Глобальна змінна лежить у `.data` процесу, який один для всіх threads. Локальна змінна лежить на stack того thread, що виконує функцію, а кожен thread має власний stack, тому в нього своя `local`.

```
Process
│
├── Code       ← shared
├── Data       ← shared
├── Heap       ← shared
│
├── Thread 1
│     └── Stack 1   ← власний
│
└── Thread 2
      └── Stack 2   ← власний
```

## 5. Race condition: `race.c`

Два threads, кожен по 1 000 000 разів робить `counter++` без захисту. Очікується `2000000`.

П'ять перших запусків:

| Run | Expected | Actual |
|---:|---:|---:|
| 1 | 2000000 | 2000000 |
| 2 | 2000000 | 2000000 |
| 3 | 2000000 | 2000000 |
| 4 | 2000000 | **1114953** |
| 5 | 2000000 | 2000000 |

Тут помилка трапилась лише один раз із п'яти. Тому я перевірив докладніше:

| Умови | Запусків | Неправильний результат | Мінімум | Медіана | Максимум |
|---|---:|---:|---:|---:|---:|
| 2 threads × 1 000 000 | 100 | **10** | 1 000 000 | 2 000 000 | 2 000 000 |
| 2 threads × 10 000 000 (`-DITERATIONS=10000000`) | 20 | **20** | 11 090 365 | 14 123 562 | 19 944 325 |

П'ять запусків при 10 000 000 ітерацій (очікувалося 20 000 000): `15207094`, `15872485`, `15309868`, `13231287`, `11360278`.

Спостереження:
- на малій кількості ітерацій thread 1 може майже закінчити роботу до того, як стартує thread 2 (старт threads займає час), тому перетин по часу невеликий і помилка трапляється рідко;
- при більшій кількості ітерацій threads гарантовано працюють одночасно, і неправильним є **кожен** запуск;
- результати щоразу різні: це залежить від timing і interleaving;
- найгірший випадок `1000000` означає, що майже всі інкременти одного thread були втрачені;
- **успішні запуски нічого не доводять**: програма некоректна, навіть якщо кілька разів вийшло `2000000`.

(З `-O2` на 1 000 000 всі 20 запусків дали `2000000`: компілятор замінив весь цикл на одну інструкцію, див. розділ 7. Це не робить програму коректною.)

## 6. Lost update

У C один рядок `counter++`, а концептуально це три кроки:

```
READ counter → ADD 1 → WRITE counter
```

Нехай `counter = 100`. Можливий interleaving:

```
Thread A                 Thread B

READ 100
                         READ 100
ADD → 101
                         ADD → 101
WRITE 101
                         WRITE 101
```

Очікували `102`, отримали `101`: інкремент Thread A **втрачено**, бо Thread B прочитав старе значення, до того як A записав нове. Це lost update.

## 7. Машинні інструкції для `counter++`

```
gcc -Wall -Wextra -pthread -O0 -S -masm=intel race.c -o race.s
objdump -d -M intel race
```

Фрагмент `<increment>` (`-O0`):

```
11bf:  48 8b 05 52 2e 00 00   mov    rax,QWORD PTR [rip+0x2e52]   # 4018 <counter>   ← READ
11c6:  48 83 c0 01            add    rax,0x1                                           ← ADD 1
11ca:  48 89 05 47 2e 00 00   mov    QWORD PTR [rip+0x2e47],rax   # 4018 <counter>   ← WRITE
11d1:  48 83 45 f8 01         add    QWORD PTR [rbp-0x8],0x1       ← i++
11d6:  48 81 7d f8 3f 42 0f 00 cmp   QWORD PTR [rbp-0x8],0xf423f   ← i <= 999999
11de:  7e df                  jle    11bf <increment+0x16>
```

**Чи виглядає `counter++` як одна неподільна операція?** Ні. Це три окремі інструкції: `mov` (читання з пам'яті в регістр), `add` (збільшення у регістрі), `mov` (запис назад). Між ними будь-який інший thread може прочитати або записати `counter`, і саме це дає lost update.

Одна C-операція це не одна інструкція процесора, а процесор може перемкнутись між threads між будь-якими двома інструкціями (зв'язок із Lab 2).

З `-O2` (для порівняння) весь цикл звівся до однієї інструкції:

```
increment:
    endbr64
    add     QWORD PTR counter[rip], 1000000
    xor     eax, eax
    ret
```

Це пояснює, чому з `-O2` гонка не проявилась: вікно для втрати майже зникло. Але інструкція все одно не має префікса `lock`, тобто не гарантовано атомарна: коректність тримається на везінні, а не на гарантії.

## 8. Що саме в програмі є race condition

```
Thread 1 ───┐
            ▼
          counter
            ▲
Thread 2 ───┘
```

```
Shared state:       змінна counter (глобальна long)
Concurrent writers: thread1 та thread2 (обидва виконують increment)
Critical operation: counter++  (READ + MODIFY + WRITE)
```

Race condition: результат залежить від того, як перемежовуються (interleave) операції threads, а це визначається timing і scheduler.

## 9. Critical section і mutex

Критична операція це `counter++`. Потрібно, щоб поки один thread її виконує, другий чекав:

```
Thread A         Thread B
LOCK             LOCK  ← чекає, поки A не віддасть
counter++
UNLOCK
                 counter++
                 UNLOCK
```

Для цього використовується mutex (mutual exclusion): `pthread_mutex_lock()` перед критичною секцією і `pthread_mutex_unlock()` після.

## 10. Виправлення: `mutex_counter.c`

Результати п'яти запусків і порівняння з `race.c` (ті самі п'ять запусків із розділу 5):

| Run | `race.c` | `mutex_counter.c` |
|---:|---:|---:|
| 1 | 2000000 | 2000000 |
| 2 | 2000000 | 2000000 |
| 3 | 2000000 | 2000000 |
| 4 | **1114953** | 2000000 |
| 5 | 2000000 | 2000000 |

Для `race.c` це лише пощастило в 4 запусках, а `mutex_counter.c` дає правильний результат завжди (перевірив і при 10 000 000 ітерацій у розділі 12).

**Чому mutex змінив поведінку?** `pthread_mutex_lock()` пускає в критичну секцію лише один thread. Якщо mutex вже належить іншому, thread блокується й чекає, поки власник викличе `pthread_mutex_unlock()`. Тому READ, MODIFY, WRITE одного thread не перемежовуються з такими самими кроками іншого, і втрати оновлень немає. Це mutual exclusion: у critical section одночасно не більше одного thread.

```
            Mutex
              │
      ┌───────┴───────┐
 Thread A         Thread B
```

## 11. Де має бути lock: `mutex_wide.c`

Два варіанти:

```c
/* вузький: lock на кожну ітерацію (mutex_counter.c) */
for (...) { lock; counter++; unlock; }

/* широкий: lock на весь цикл (mutex_wide.c) */
lock; for (...) { counter++; } unlock;
```

Обидва правильні (`mutex_wide` теж дав `2000000` в усіх запусках). Різниця в тому, як працюють threads:

```
Thread A  ── holds mutex ──[ 1 000 000 increments ]──
Thread B  ── WAIT ───────────────────────────────────  потім свої 1 000 000
```

У широкому варіанті Thread B нічого не робить, доки A не закінчить, тобто паралелізму немає: threads працюють по черзі. У вузькому варіанті threads чергуються на кожному кроці. Висновок: critical section має бути достатньою для correctness, але без потреби не надто великою.

(У цій програмі, де вся робота і є critical section, широкий lock вийшов навіть швидшим, див. розділ 12: немає боротьби за mutex на кожному кроці. Але в реальній програмі, де в threads є ще й некритична робота, широкий lock зведе паралелізм нанівець.)

## 12. Synchronization має вартість

Час виконання (`real`, три запуски):

| Програма | Run 1 | Run 2 | Run 3 |
|---|---:|---:|---:|
| `race` (1M) | 0,009 с | 0,009 с | 0,009 с |
| `mutex_counter` (1M) | 0,124 с | 0,096 с | 0,131 с |
| `mutex_wide` (1M) | 0,007 с | 0,007 с | 0,012 с |
| `race` (10M) | 0,057 с | 0,049 с | 0,050 с |
| `mutex_counter` (10M) | 1,105 с | 1,374 с | 1,208 с |
| `mutex_wide` (10M) | 0,045 с | 0,046 с | 0,047 с |

`mutex_counter` у 10–25 разів повільніший за `race`. Це не точний benchmark, а демонстрація концепції. У `time` видно, куди йде час: при 10M ітерацій у `mutex_counter` `sys` ≈ 0,4–0,6 с (звернення до ядра через futex), а в `race` майже 0.

**Чому synchronized програма може бути повільнішою?**
- кожне `lock`/`unlock` це додаткові операції, а коли mutex зайнятий, thread засинає й ядро його будить (системні виклики);
- lock contention: threads змагаються за один mutex, і замість роботи чекають;
- в кожній ітерації мільйон разів платимо за синхронізацію заради однієї інструкції.

```
Synchronization → correctness + overhead / contention
```

## 13. Більше threads: `race_four.c`, `mutex_four.c`

4 threads × 500 000 increments, очікується `2000000`.

`race_four` (без mutex), п'ять запусків: `1677442`, `2000000`, `1162875`, `1084634`, `1258489`.
`mutex_four` (з mutex), п'ять запусків: `2000000` у всіх.

| Варіант | Неправильних результатів | Типовий час |
|---|---|---:|
| 2 threads без mutex | 10 зі 100 | 0,009 с |
| 4 threads без mutex | **87 зі 100** (мінімум 273 015) | 0,008 с |
| 2 threads з mutex | 0 з 5 | 0,096–0,131 с |
| 4 threads з mutex | 0 з 5 | 0,099–0,135 с |

**Чи означає більше threads автоматично швидшу програму?** Ні. Тут:
- без mutex чотири threads лише збільшили кількість помилок: майже кожен запуск неправильний;
- з mutex чотири threads не швидші за два (0,10–0,13 с проти 0,10–0,13 с), бо працювати може лише один thread за раз, а решта чекають; до того ж у машині лише 2 ядра;
- швидше стає тільки тоді, коли threads справді працюють одночасно над незалежними частинами, як у `parallel_sum`.

## 14. Shared heap: `shared_heap.c`

```
$ ./shared_heap
Worker: value=110 address=0x55bb4fe372a0
Main: value=110 address=0x55bb4fe372a0
```

**Де знаходиться `data`?** У heap (виділена через `malloc`; адреса `0x55bb...` разом з образом програми, а не `0x7ff...`, як stack).
**Чи бачить worker ту саму пам'ять?** Так: однакова адреса, і Main прочитав `110`, тобто зміну, зроблену worker.
**Чому?** Heap один на весь процес, а ми передали thread вказівник. Thread має власний stack, але heap спільний.
**Що змінилося б, якби кілька threads одночасно робили `data->value += 10`?** Вийшла б така сама race condition, як із `counter++`: `+=` це теж READ-MODIFY-WRITE, тому частина збільшень втрачалась би (потрібен mutex).

## 15. Повернення результату: `thread_result.c`

```
$ ./thread_result
Result = 144
```

**Чому не можна `int result = value * value; return &result;`?** `result` це локальна змінна, і вона лежить на stack thread-а. Коли функція повертається (thread завершується), цей stack перестає існувати. Вказівник `&result` вказує на пам'ять, якої вже немає (dangling pointer), і читати її це undefined behavior. Тому результат створюється в heap через `malloc`: heap живе, доки його не звільнять, і main після `pthread_join` отримує коректний вказівник (і сам робить `free`).

```
result → local variable → stack thread-а → зникає, коли функція завершилась
```

## 16. Deadlock: спочатку аналіз

```
Thread A:  lock(mutex1)  →  lock(mutex2)
Thread B:  lock(mutex2)  →  lock(mutex1)
```

Можливе виконання:

```
Thread A                  Thread B

lock mutex1               lock mutex2     ← кожен узяв по одному

lock mutex2 ✗ чекає       lock mutex1 ✗ чекає
(належить B)              (належить A)

       ↓                      ↓
             DEADLOCK
```

Обидва можуть зупинитись назавжди: A тримає mutex1 і чекає на mutex2, а B тримає mutex2 і чекає на mutex1. Жоден не може продовжити, бо чекає на те, що утримує інший, і жоден не віддасть свій mutex, поки не отримає другий.

## 17. Спостереження: `deadlock.c`

```
$ ./deadlock
Thread 1: locking mutex1
Thread 2: locking mutex2
Thread 1: locking mutex2
Thread 2: locking mutex1
                              ← далі нічого, програма зависла
```

Тут не з'являється «critical section» ні в одного thread. Три запуски під `timeout 4` усі завершились кодом `124`, тобто програма не завершилась сама.

Стан завислого процесу (`ps -L`):

```
  PID   TID S WCHAN                CMD
 1940  1940 S futex_do_wait        ./deadlock      ← main (чекає pthread_join)
 1940  1942 S futex_do_wait        ./deadlock      ← Thread 1
 1940  1943 S futex_do_wait        ./deadlock      ← Thread 2
```

Усі три threads у стані `S` і чекають на futex; `/proc/PID/status` показує `Threads: 3`; `utime=0 stime=0`, тобто CPU не споживається. Через 6 секунд процес досі живий. (Це також ще один спосіб побачити: у процесі один PID, а threads мають різні TID.)

Є деталь: якщо перенаправити вивід у файл (`./deadlock > out.txt`), у файлі буде порожньо (0 байтів), бо `stdout` буферизується, а програма ніколи не завершується й не скидає буфер. Щоб побачити рядки, я запускав через `stdbuf -oL`.

```
Thread 1 → хоче mutex2 → належить Thread 2
   ▲                              │
   │                              ▼
   └──── mutex1 ◄── хоче ── Thread 2
```

Це **circular wait**: Thread 1 → mutex2 → Thread 2 → mutex1 → Thread 1.

## 18. Виправлення: `deadlock_fixed.c`

У `worker2` замінив порядок на `mutex1`, потім `mutex2` (як у `worker1`):

```
$ ./deadlock_fixed
Thread 2: locking mutex1
Thread 1: locking mutex1
Thread 2: locking mutex2
Thread 2: critical section
Thread 1: locking mutex2
Thread 1: critical section

real    0m2.003s
```

Програма завершилась (код 0) в усіх п'яти запусках. Час 2 секунди: Thread 2 тримає mutex1 і спить `sleep(1)`, потім Thread 1 чекає й бере його ще на секунду.

**Яку умову deadlock усунули?** Circular wait (циклічне очікування). Коли всі threads беруть mutex у одному порядку (спершу mutex1, потім mutex2), цикл «A чекає B, B чекає A» неможливий: той, хто взяв mutex1 першим, завжди зможе взяти й mutex2, бо другий thread зупиниться ще на mutex1.

## 19. Race condition ≠ deadlock

| Характеристика | Race Condition | Deadlock |
|---|---|---|
| Threads продовжують execution? | Так, виконуються далі | Ні, заблоковані назавжди |
| Результат може бути неправильним? | Так (1114953 замість 2000000) | Результату взагалі немає, програма зависає |
| Програма може повністю перестати прогресувати? | Ні | Так |
| Пов'язано з timing/order? | Так (interleaving) | Так (залежить від порядку взяття lock) |
| Mutex може допомогти? | Так, це основний засіб | Ні: mutex якраз і причина |
| Неправильне використання mutex може бути причиною? | Так: відсутній або неповний захист | Так: неправильний порядок блокувань |

```
No synchronization        →  Race Condition
Incorrect synchronization →  Deadlock
```

Synchronization потрібна, але її теж треба проєктувати правильно.

## 20. Фінальне завдання: `parallel_sum.c`

Сума 1 + 2 + … + N на 4 threads; кожен рахує свій діапазон у локальній змінній `sum` і записує результат у власну структуру `Task`.

```
$ ./parallel_sum
Thread 1: 1 ... 250000 = 31250125000
Thread 2: 250001 ... 500000 = 93750125000
Thread 3: 500001 ... 750000 = 156250125000
Thread 4: 750001 ... 1000000 = 218750125000

Parallel result: 500000500000
Expected result: 500000500000

Correct: YES
```

Перевірка за формулою `N × (N + 1) / 2 = 1000000 × 1000001 / 2 = 500000500000` збігається. Програма також правильно працює, якщо N не ділиться на 4 (`./parallel_sum 1000003` дало `500003500006`, `Correct: YES`; останній thread бере залишок), а також з `N = 1 000 000 000` (`500000000500000000`).

### Аналіз

**1. Які data shared?** Масив `tasks` (доступний main і worker threads через вказівник), а також усі глобальні дані та heap процесу.
**2. Які data thread-local?** Змінна `sum` усередині `calculate_sum()` і лічильник циклу `i`: вони на stack кожного thread.
**3. Чому threads не потребують mutex у циклі?** Кожен thread змінює лише власний local accumulator і власний `Task`. Ніхто більше їх не чіпає, тому немає ні shared mutable state, ні гонки.
**4. Коли main читає результати?** Лише після `pthread_join()` для відповідного thread. Join гарантує, що thread закінчив запис `task->result`.
**5. Чому цей design кращий за один глобальний counter з lock на кожній ітерації?** Синхронізація потрібна один раз на thread (при збиранні результатів), а не 250 000 разів. З розділу 12 видно, що lock на кожному кроці може коштувати в десятки разів повільніше. Найкращий спосіб розв'язати race condition інколи не додавати більше locks, а зменшити shared mutable state.

### Додатково: sequential проти 4 threads

`sequential_sum.c` рахує те саме в одному thread.

| N | `sequential_sum` (real) | `parallel_sum` (real) |
|---|---|---|
| 1 000 000 | 0,005 с (×3) | 0,004 с (×3) |
| 1 000 000 000 | 2,653 / 2,658 / 2,705 с | 1,134 / 1,126 / 1,195 с |

Для 1 000 000 різниця непомітна: самої роботи так мало, що вона співмірна з вартістю створення threads. Для великого N 4 threads дали виграш ≈ 2,3 рази, а не 4: у машині лише 2 ядра (вище за 2 не стрибнеш; частина виграшу в тому, що цикл у `parallel_sum` при `-O0` трохи дешевший за цикл у `sequential_sum`, видно з `user` часу).

**За яких умов parallelization має сенс?**
- задача достатньо велика, щоб вартість створення threads була малою порівняно з роботою;
- її можна розділити на незалежні частини, які майже не потребують спільних даних і блокувань;
- є достатньо ядер (4 threads на 2 ядрах не дадуть 4× швидкості);
- результати збираються рідко (раз наприкінці), а не на кожному кроці.

## Відповіді на контрольні питання

1. **Що таке thread?** Одиниця виконання всередині процесу зі своїм стеком і регістрами. Процес може мати кілька threads.
2. **Чим thread відрізняється від process?** Процеси мають окремі адресні простори (як після `fork`), а threads одного процесу діляться одним адресним простором. Створити thread дешевше, але вони легше заважають одне одному.
3. **Що threads одного процесу поділяють?** Код, глобальні й static дані (`.data`, `.bss`), heap, відкриті файли.
4. **Що кожен thread має власне?** Stack, регістри (включно з лічильником інструкцій), власний ідентифікатор (TID).
5. **Чи має кожен thread власний stack?** Так (`local` у `thread_stacks` мають різні адреси, на 8 МБ + 4 КБ одна від одної).
6. **Чи мають threads спільний heap?** Так, `shared_heap` показав однакову адресу та зміну значення.
7. **Для чого `pthread_create()`?** Створює новий thread, який починає виконувати вказану функцію з переданим аргументом.
8. **Для чого `pthread_join()`?** Чекає завершення thread і (за потреби) забирає його результат.
9. **Чи гарантується порядок виконання threads порядком `pthread_create()`?** Ні, його визначає scheduler (у `multiple_threads` порядок щоразу різний).
10. **Concurrency проти parallelism?** Concurrency означає, що кілька задач просуваються в перемежованому порядку (можливо, на одному ядрі). Parallelism означає, що вони справді виконуються одночасно на різних ядрах.
11. **Shared state?** Дані, до яких мають доступ кілька threads (тут `counter`).
12. **Race condition?** Ситуація, коли результат залежить від порядку або timing виконання threads, що одночасно звертаються до shared state (хоча б один пише).
13. **Lost update?** Оновлення, перезаписане іншим thread-ом: обидва прочитали старе значення, і один запис «затер» інший (101 замість 102).
14. **Чому `counter++` не atomic?** Це три інструкції (`mov` читання, `add`, `mov` запис), і між ними може втрутитись інший thread.
15. **Critical section?** Ділянка коду, яка працює із shared state й не має виконуватись одночасно кількома threads (`counter++`).
16. **Mutual exclusion?** Гарантія, що в critical section у кожен момент не більше одного thread.
17. **Mutex?** Об'єкт-замок, який реалізує mutual exclusion: його може тримати лише один thread.
18. **Що робить `pthread_mutex_lock()`?** Захоплює mutex; якщо він вільний, thread одразу проходить далі.
19. **Що, якщо mutex уже належить іншому thread?** Thread блокується (засинає), доки власник не викличе unlock.
20. **Навіщо `pthread_mutex_unlock()`?** Віддає mutex, щоб інші threads могли зайти в critical section. Без unlock всі інші чекали б вічно.
21. **Чому надто велика critical section погіршує concurrency?** Бо поки один thread тримає mutex, решта чекають, і паралелізм зникає (`mutex_wide`: Thread B стоїть, доки A не зробить мільйон кроків).
22. **Lock contention?** Конкуренція threads за один і той самий lock: вони витрачають час на очікування (у `mutex_counter` це дало 10–25× повільнішу роботу).
23. **Чому більше threads не обов'язково означає більшу performance?** Ядер обмежена кількість, threads потрібно створювати, синхронізувати й чекати один на одного (4 threads з mutex не швидші за 2; без mutex у 4 threads 87% запусків неправильні).
24. **Deadlock?** Стан, коли threads чекають одне на одного нескінченно й жоден не може продовжити (`deadlock.c`).
25. **Чим deadlock відрізняється від race condition?** Race: програма працює, але результат може бути неправильний. Deadlock: програма зависає й результату немає; його спричиняє неправильне використання locks.
26. **Circular wait?** Цикл очікування: Thread 1 чекає ресурс Thread 2, а Thread 2 чекає ресурс Thread 1.
27. **Як однаковий порядок блокувань допомагає?** Усуває circular wait: коли всі беруть mutex у тому самому порядку, цикл неможливий (`deadlock_fixed`).
28. **Starvation?** Ситуація, коли thread дуже довго (можливо, нескінченно) не отримує потрібного ресурсу (наприклад, mutex), бо його постійно випереджають інші, хоч програма в цілому працює.
29. **Чому local accumulation краще за shared counter із mutex на кожній ітерації?** Синхронізація потрібна один раз, а не мільйон; threads не конкурують за lock і справді працюють паралельно.
30. **Чому 100 успішних запусків не доводять відсутність race condition?** Гонка залежить від timing: у `race.c` 90 запусків зі 100 дали правильний результат, але програма все одно некоректна. Відсутність помилки у тестах не доводить відсутність помилки в програмі.

## Короткий висновок

Експериментально встановлено:

- threads одного процесу діляться пам'яттю (код, дані, heap): адреса `value` і `shared_heap` однакова для всіх threads; але кожен thread має власний stack (8 МБ, `local` відрізняються на `0x801000`);
- порядок threads не гарантований: у `multiple_threads` було кілька різних порядків;
- `counter++` це три інструкції (`mov`, `add`, `mov`), тому два threads без синхронізації втрачають оновлення: `1114953` замість `2000000`, на 10M ітерацій помилка в кожному запуску;
- гонка проявляється нерегулярно (10 зі 100 запусків на 1M ітерацій), тому тестами її відсутність довести не можна;
- `mutex` забезпечує mutual exclusion і виправляє результат (5 із 5), але має ціну: lock на кожній ітерації в 10–25 разів повільніший, а широкий lock прибирає паралелізм;
- більше threads не означає швидше: 4 threads з mutex не швидші за 2, а без mutex помилок ще більше;
- deadlock виникає через circular wait (протилежний порядок lock); усі threads сплять у `futex_wait` і не споживають CPU; однаковий порядок блокувань його усуває;
- найкращий спосіб уникнути race condition це зменшити shared mutable state: `parallel_sum` дає правильний результат без жодного mutex і на великому N у ≈2,3 рази швидший за послідовну версію.
