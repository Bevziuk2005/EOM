## Завдання 1. Розміри типів

| Тип | Розмір, bytes | Розмір, bits |
|-----|:---:|:---:|
| char | 1 | 8 |
| short | 2 | 16 |
| int | 4 | 32 |
| long | 8 | 64 |
| long long | 8 | 64 |
| float | 4 | 32 |
| double | 8 | 64 |
| void * | 8 | 64 |

**Чи всі типи займають однакову кількість пам'яті?**
Ні. Від 1 байта (`char`) до 8 байтів (`long`, `double`, вказівник).

**Скільки бітів займає `int`?**
32 біти (4 байти).

**Який розмір має `void *`?**
8 байтів.

**Що це говорить про архітектуру?**
Вказівник зберігає адресу, тому його розмір відповідає розміру адреси на машині. 8 байтів = 64 біти, отже середовище 64-бітне (x86-64). Це збігається з `uname -m`.

Ще помітив, що `long` тут 8 байтів, хоча `int` лише 4. Тобто розмір типів залежить від платформи, а в стандарті C гарантовано тільки `sizeof(char) == 1`.

## Завдання 2. Decimal → Hexadecimal

| Decimal | Hexadecimal | Binary |
|--------:|:-----------:|:------:|
| 10 | 0xA | 1010 |
| 65 | 0x41 | 1000001 |
| 127 | 0x7F | 1111111 |
| 255 | 0xFF | 11111111 |
| 256 | 0x100 | 100000000 |
| 1024 | 0x400 | 10000000000 |

(спочатку розраховував вручну, потім звірив з виводом програми — збіглось)

**Чому `65`, `0x41` і `01000001` — це те саме значення?**
Це три способи записати одне число, як «сорок п'ять» і «45». У пам'яті лежить один і той самий набір бітів. Система числення — це лише наш спосіб його показати:
- decimal: 6·10 + 5 = 65
- hex: 4·16 + 1 = 65
- binary: 64 + 1 = 65

Hex зручний ще й тому, що одна шістнадцяткова цифра рівно відповідає 4 бітам, тож байт — це завжди дві hex-цифри (`0100 0001` → `4` і `1`).

## Завдання 3. Виведення бітів

Функція `print_binary(unsigned char value)` в `binary.c`. Результати:

| Decimal | Hex | Binary |
|--------:|:---:|:------:|
| 0 | 0x00 | 00000000 |
| 1 | 0x01 | 00000001 |
| 10 | 0x0A | 00001010 |
| 65 | 0x41 | 01000001 |
| 127 | 0x7F | 01111111 |
| 128 | 0x80 | 10000000 |
| 255 | 0xFF | 11111111 |

**Чому перевірка починається з біта 7, а не з біта 0?**
Біт 7 — старший. Числа ми читаємо зліва направо, від старшого розряду до молодшого, так само як `65` — спочатку десятки, потім одиниці. Якщо йти від біта 0, число вийде записане задом наперед (для 65 було б `10000010`).

## Завдання 4. Символ — це також число

| Character | Decimal | Hex |
|:---------:|--------:|:---:|
| A | 65 | 0x41 |
| B | 66 | 0x42 |
| a | 97 | 0x61 |
| 0 | 48 | 0x30 |
| 9 | 57 | 0x39 |

**Що зберігається в `char c = 'A';`?**
Число 65 (один байт `01000001`). Літери як такої в пам'яті немає. Коли `printf` отримує `%c`, він бере це число й за таблицею ASCII малює символ `A`; коли отримує `%d`, то просто друкує число. Підтвердження — вираз `'A' + 1` дає 66, тобто `'B'`.

Також цікаво: символ `'0'` — це не число 0, а код 48. Цифра-символ і цифра-число — різні речі.

## Завдання 5. Signed та Unsigned

**Прогноз до запуску:** для `-1` у `int8_t` очікую `11111111`. Логіка: у two's complement мінус одиниця — це «усі біти одиниці» (інвертуємо `00000001` → `11111110` і додаємо 1 → `11111111`).

**Результат:**

```
int8_t  = -1
uint8_t = 255

int8_t  (-1)  hex: 0xFF  bits: 11111111
uint8_t (255) hex: 0xFF  bits: 11111111
```

Прогноз підтвердився: біти в обох змінних однакові.

**Як `11111111` може бути і 255, і -1?**
Біти однакові, відрізняється правило, за яким їх читають. Для `uint8_t` усі 8 бітів — це величина: 128+64+32+16+8+4+2+1 = 255. Для `int8_t` старший біт має вагу −128, тому: −128 + 127 = −1. Значення визначає **тип**, а не самі біти.

---

## Завдання 6. Межа unsigned integer

**Прогноз до запуску:** `255 + 1` у `uint8_t` дасть `0`. У байті лише 8 бітів, результат 256 = `1 0000 0000` потребує дев'ятого біта, якого немає, тож він відкидається і залишається `00000000`.

Під час обчислення `a + 1` значення `a` спочатку підвищується до `int` (integer promotion), тому вираз розраховується як `256`, а потім результат зберігається в `uint8_t`, де він обгортається за модулем 256.

**Результат:**

```
Before: 255
After value++: 0

254         -> 254
255         -> 255
255 + 1     -> 0
255 + 2     -> 1
```

Прогноз підтвердився. Фактично `uint8_t` рахує за модулем 256: після 255 знову 0, потім 1 і так по колу.

Для `uint8_t` діапазон 0…255 (2⁸ значень), і при переході через верхню межу відбувається «обгортання». Цю поведінку я перевіряв саме для беззнакового типу. На знакові типи її переносити не можна: у C signed overflow — це undefined behavior, там компілятор нічого не гарантує.

## Завдання 7–8. Пам'ять та endianness

**Гіпотеза до запуску:** число `0x12345678` займає 4 байти. На x86 я очікую варіант **B**, тобто `78 56 34 12` (молодший байт за найменшою адресою), бо це має бути little-endian.

**Фактичний результат:**

```
value = 0x12345678

byte 0 = 0x78
byte 1 = 0x56
byte 2 = 0x34
byte 3 = 0x12

Address              Value
0x7ffff5824984       0x78
0x7ffff5824985       0x56
0x7ffff5824986       0x34
0x7ffff5824987       0x12
```

Гіпотеза підтвердилась: варіант B.

**У якому напрямку змінюються адреси?**
Зростають: `...764` → `...765` → `...766` → `...767` (кожна на 1 байт більша).

**Який байт лежить за найменшою адресою?**
`0x78` — молодший байт числа.

**Чому це little-endian?**
Бо молодший байт стоїть першим, за найменшою адресою, а старший `0x12` — останнім. У big-endian було б навпаки: `12 34 56 78`.

**Чи змінилось саме число?**
Ні. Значення залишається `0x12345678`, коли ми читаємо його як `uint32_t`. Змінюється лише те, як байти розкладені в пам'яті. Тому порядок байтів важливо враховувати, коли дивимось на пам'ять побайтово (мережеві протоколи, файли, дампи).

---

## Завдання 9. Одні біти — різні інтерпретації

| Інтерпретація | Значення |
|---------------|----------|
| Binary | 01000001 |
| Hexadecimal | 0x41 |
| Unsigned decimal | 65 |
| ASCII character | A |

**Чому комп'ютеру недостатньо знати лише біти?**
Бо біти самі по собі нічого не означають. Той самий байт `01000001` — це і число 65, і літера `A`, і частина адреси чи кольору. Щоб отримати значення, потрібні **тип** (`uint8_t`, `int8_t`, `char`...), що задає правило **інтерпретації**, і **контекст** (як програма це використовує і яким форматом ми це виводимо). Без типу й контексту `11111111` може бути 255, −1 чи просто «усі біти увімкнено».


## Відповіді на контрольні питання

1. **Що таке біт і байт?** Біт — найменша одиниця інформації, 0 або 1. Байт — 8 бітів, найменша адресована одиниця пам'яті.
2. **Скільки значень можна представити за допомогою n бітів?** 2ⁿ.
3. **Діапазон 8-бітного unsigned:** 0…255.
4. **Діапазон 8-бітного signed (two's complement):** −128…127.
5. **Чому hex зручний?** Одна hex-цифра = 4 біти, байт = 2 цифри. Запис короткий, а перетворення в біти й назад майже миттєве.
6. **Чим відрізняється `11111111` як `uint8_t` та `int8_t`?** Біти ті самі; як `uint8_t` це 255, як `int8_t` це −1.
7. **Що буде після збільшення `uint8_t` зі значенням 255?** Стане 0 (обгортання за модулем 256).
8. **Що зберігається в пам'яті для символу `A`?** Число 65 (`0x41`, `01000001`).
9. **Що таке endianness?** Порядок, у якому байти багатобайтового значення розташовані в пам'яті.
10. **Який порядок на досліджуваній x86-64 системі?** Little-endian.
11. **Що означає `sizeof(int)`?** Розмір типу `int` у байтах для поточного компілятора і платформи (тут 4).
12. **Чому одні й ті самі біти можуть представляти різні дані?** Бо їхнє значення задається типом та контекстом, а не самими бітами.

---

## Короткий підсумок

Експериментально встановлено:

- на цій системі `int` = 4 байти, `long` і `void *` = 8 байтів, отже середовище 64-бітне;
- 65, `0x41` і `01000001` — один і той самий байт у різних записах;
- символ у C — це число (`'A'` = 65), літерою його робить лише виведення;
- `11111111` читається як 255 (`uint8_t`) або −1 (`int8_t`), залежно від типу;
- `uint8_t` після 255 переходить у 0, бо для результату просто немає 9-го біта;
- на x86-64 байти зберігаються за схемою little-endian: у `0x12345678` за найменшою адресою лежить `0x78`.

Головний висновок: пам'ять зберігає лише біти, а їхній сенс задають тип і спосіб інтерпретації.

## Підготовка. `arithmetic.c`

дістати значення `a` з пам'яті, дістати значення `b`, скласти їх десь усередині процесора і записати суму назад у пам'ять у змінну `result`.

## Завдання 1. Отримуємо Assembly

```
gcc -Wall -Wextra -O0 -S -masm=intel arithmetic.c -o arithmetic_intel.s
```

Тіло `main` (без службових директив `.cfi`):

```asm
main:
    endbr64
    push    rbp
    mov     rbp, rsp
    sub     rsp, 16
    mov     DWORD PTR -12[rbp], 5        ; a = 5
    mov     DWORD PTR -8[rbp], 7         ; b = 7
    mov     edx, DWORD PTR -12[rbp]      ; edx = a
    mov     eax, DWORD PTR -8[rbp]       ; eax = b
    add     eax, edx                     ; eax = a + b
    mov     DWORD PTR -4[rbp], eax       ; result = eax
    mov     eax, DWORD PTR -4[rbp]
    mov     esi, eax                     ; 2-й аргумент printf
    lea     rax, .LC0[rip]               ; адреса рядка "Result: %d\n"
    mov     rdi, rax                     ; 1-й аргумент printf
    mov     eax, 0
    call    printf@PLT
    mov     eax, 0                       ; return 0
    leave
    ret
```

Знайшов:
- функція `main` — мітка `main:`;
- `mov` — багато разів (пересилання значень);
- додавання — `add eax, edx`;
- виклик `printf` — `call printf@PLT`;
- `ret` в кінці.

**Чи кожному рядку C відповідає рівно одна інструкція?**
Ні. Рядок `int result = a + b;` перетворився на чотири інструкції (`mov`, `mov`, `add`, `mov`), а `printf(...)` — на цілу групу (підготувати аргументи + `call`).

**Чи є в Assembly змінні `a`, `b`, `result`?**
Ні, імен немає. Є лише місця в пам'яті відносно `rbp`: `a` лежить за `[rbp-12]`, `b` за `[rbp-8]`, `result` за `[rbp-4]`. Імена змінних потрібні людині та компілятору, процесору вони не потрібні.

**Скільки інструкцій у `main()`?**
Від `endbr64` до `ret` вийшло 19 інструкцій, при тому що в тілі `main` усього 5 рядків C.

**Чи є додавання?**
Так, `add eax, edx`.

## Завдання 2. Арифметична операція

`operations.c` працює і виводить `30`. Функція `calculate` в Assembly:

```asm
calculate:
    endbr64
    push    rbp
    mov     rbp, rsp
    mov     DWORD PTR -20[rbp], edi      ; параметр a прийшов у edi
    mov     DWORD PTR -24[rbp], esi      ; параметр b прийшов у esi
    mov     edx, DWORD PTR -20[rbp]
    mov     eax, DWORD PTR -24[rbp]
    add     eax, edx                     ; a + b
    mov     DWORD PTR -4[rbp], eax       ; result
    mov     eax, DWORD PTR -4[rbp]       ; готуємо значення для повернення
    pop     rbp
    ret
```

Регістри: `edi` і `esi` — аргументи функції (перший і другий), `eax` — тут рахується сума й одночасно звідти повертається результат, `edx` — допоміжний.

**Експеримент.** Підміняв рядок з обчисленням на `a + b`, `a - b`, `a * b`, щоразу збирав `-O0 -S -masm=intel`:

| C | Основна Assembly-інструкція | Як виглядає |
|---|---|---|
| `a + b` | `add` | `add eax, edx` |
| `a - b` | `sub` | `sub eax, DWORD PTR -24[rbp]` |
| `a * b` | `imul` | `imul eax, DWORD PTR -24[rbp]` |

**Що змінилось після заміни однієї операції?**
Практично тільки одна інструкція: `add` → `sub` → `imul`. Решта (збереження аргументів, `push rbp`, повернення через `eax`, `ret`) залишилась такою самою. Для `-` і `*` компілятор ще й одразу бере другий операнд із пам'яті, тому зникла окрема пара `mov edx...`/`mov eax...`. Тобто змінюючи оператор у C, ми змінюємо саме арифметичну інструкцію.

## Завдання 3. `if`

`condition.c` працює і виводить `20`. Функція `max_value`:

```asm
max_value:
    endbr64
    push    rbp
    mov     rbp, rsp
    mov     DWORD PTR -4[rbp], edi       ; a
    mov     DWORD PTR -8[rbp], esi       ; b
    mov     eax, DWORD PTR -4[rbp]       ; eax = a
    cmp     eax, DWORD PTR -8[rbp]       ; порівняти a і b
    jle     .L2                          ; якщо a <= b — стрибок на else
    mov     eax, DWORD PTR -4[rbp]       ; return a
    jmp     .L3                          ; пропустити else
.L2:
    mov     eax, DWORD PTR -8[rbp]       ; return b
.L3:
    pop     rbp
    ret
```

Відповідність:

```
C                       Assembly

if (a > b)        →     mov eax, [a]
                        cmp eax, [b]
                        jle .L2          (стрибок, якщо умова НЕ виконана)

return a          →     mov eax, [a]
                        jmp .L3

else              →     мітка .L2:

return b          →     mov eax, [b]     (далі .L3: pop rbp / ret)
```

Цікаво, що компілятор «перевернув» умову: у C написано `a > b`, а стрибок стоїть на протилежну `jle`. Логіка така: якщо умова хибна, перестрибуємо на `else`, а якщо істинна, просто йдемо далі по рядках.

**Чи існує машинна інструкція `IF` у тому сенсі, як у C?**
Ні. CPU реалізує `if` двома кроками: `cmp` порівнює числа й записує результат у регістр прапорців (flags), а потім умовний перехід (`jle`, `jg`, `je`...) дивиться на ці прапорці. Якщо умова спрацювала, процесор змінює адресу наступної інструкції (стрибок), а якщо ні — виконує наступну по порядку. Дві гілки — це просто два шматки коду з мітками.

## Завдання 4. Цикл

`loop.c` працює і виводить `15`. Функція `sum_to`:

```asm
sum_to:
    endbr64
    push    rbp
    mov     rbp, rsp
    mov     DWORD PTR -20[rbp], edi      ; n
    mov     DWORD PTR -8[rbp], 0         ; sum = 0
    mov     DWORD PTR -4[rbp], 1         ; i = 1          (initialization)
    jmp     .L2                          ; одразу до перевірки умови
.L3:
    mov     eax, DWORD PTR -4[rbp]       ;                (body)
    add     DWORD PTR -8[rbp], eax       ; sum += i
    add     DWORD PTR -4[rbp], 1         ; i++            (increment)
.L2:
    mov     eax, DWORD PTR -4[rbp]
    cmp     eax, DWORD PTR -20[rbp]      ; i порівнюється з n   (condition)
    jle     .L3                          ; i <= n — стрибок назад на тіло
    mov     eax, DWORD PTR -8[rbp]       ; return sum
    pop     rbp
    ret
```

Структура цикла в Assembly:

```
i = 1                 →  mov [i], 1
перехід до умови      →  jmp .L2
.L2: умова            →  mov eax,[i] ; cmp eax,[n] ; jle .L3
.L3: тіло             →  add [sum], eax
зміна i               →  add [i], 1
стрибок назад         →  (знову .L2 → jle .L3)
вихід з циклу         →  інструкція після jle
```

Умова стоїть **після** тіла: на початку компілятор один раз стрибає на неї (`jmp .L2`), а далі умова працює як «перевірка в кінці кожного кола».

**Яка інструкція виконує порівняння?** `cmp eax, DWORD PTR -20[rbp]`.
**Яка інструкція реалізує перехід?** `jle .L3` — умовний перехід назад (і `jmp .L2` — безумовний, на самому початку).
**Чи існує в Assembly поняття `for`?** Ні, воно розкладене на `mov` (ініціалізація), `cmp`, умовний перехід, тіло, `add` (зміна `i`) і стрибок назад.
**Як CPU вирішує, що цикл треба повторити?** `cmp` виставляє прапорці за результатом порівняння `i` та `n`; `jle` дивиться на прапорці. Поки `i <= n`, стрибок виконується й керування йде на початок тіла; коли `i` стає більшим за `n`, стрибок не спрацьовує й виконується наступна інструкція після циклу.

## Завдання 5. Виклик функції

З `main` у `operations.c` (bytes та адреси — з `objdump`, див. нижче):

```asm
main:
    ...
    mov     esi, 20            ; другий аргумент
    mov     edi, 10            ; перший аргумент
    call    calculate          ; ← виклик
    mov     DWORD PTR -4[rbp], eax   ; результат повернувся в eax
```

- виклик `calculate` — `call` за адресою `0x117d`;
- код `calculate` починається за адресою `0x1149`;
- функція завершується інструкцією `ret` за адресою `0x1166`;
- результат повертається в регістрі `eax`.

**Чому після `call` CPU повинен знати, куди повертатись?**
Бо `calculate` можна викликати з будь-якого місця програми, і після `ret` треба продовжити саме там, де зупинились. Тому `call` перед стрибком запам'ятовує адресу наступної інструкції (тут `0x1182`), а `ret` дістає її й повертається. Де саме ця адреса зберігається — тема наступної лабораторної (стек).

## Завдання 6–7. Machine code

```
gcc -Wall -Wextra -O0 operations.c -o operations
objdump -d -M intel operations
```

Фрагмент `<calculate>`:

```

    114d:  55                    push   rbp
    114e:  48 89 e5              mov    rbp,rsp
    1151:  89 7d ec              mov    DWORD PTR [rbp-0x14],edi
    1154:  89 75 e8              mov    DWORD PTR [rbp-0x18],esi
    1157:  8b 55 ec              mov    edx,DWORD PTR [rbp-0x14]
    115a:  8b 45 e8              mov    eax,DWORD PTR [rbp-0x18]
    115d:  01 d0                 add    eax,edx
    115f:  89 45 fc              mov    DWORD PTR [rbp-0x4],eax
    1162:  8b 45 fc              mov    eax,DWORD PTR [rbp-0x4]
    1165:  5d                    pop    rbp
    1166:  c3                    ret
```

Три інструкції з реального файлу:

| Address | Machine-code bytes | Assembly |
|---------|--------------------|----------|
| 0x115d | `01 d0` | `add eax, edx` |
| 0x117d | `e8 c7 ff ff ff` | `call 1149 <calculate>` |
| 0x1166 | `c3` | `ret` |

Перевірив `call` руками: байти `c7 ff ff ff` — це число `0xffffffc7` = −57 (байти йдуть у little-endian, як у лабораторній 1). Наступна інструкція стоїть за адресою `0x1182`, і `0x1182 − 57 = 0x1149` — це якраз початок `calculate`. Тобто `call` зберігає не абсолютну адресу, а відстань до функції.

**Що зберігається у виконуваному файлі: текст Assembly чи machine code?**
Machine code, тобто байти. Тексту `add eax, edx` там немає.

**Навіщо тоді `objdump` показує Assembly?**
Це дизасемблер: він читає байти й перекладає їх назад у мнемоніки, щоб людина могла це прочитати. `01 d0` ↔ `add eax, edx` — це два записи однієї інструкції.

**Чи всі інструкції x86-64 мають однакову довжину?**
Ні. У цьому файлі є й 1 байт (`c3`, `55`), й 2 (`01 d0`), 3 (`48 89 e5`), 4 (`f3 0f 1e fa`), 5 (`e8 ...`), 7 (`48 8d 05 73 0e 00 00` — `lea rax, [rip+0xe73]` в `main`).

**Чому людині зручніше читати Assembly?**
Мнемоніки (`add`, `mov`, `call`) легше запам'ятати й зрозуміти, ніж шістнадцяткові байти, а адреси переходів і імена функцій `objdump` підставляє сам.

## Завдання 8. Оптимізація: `-O0` проти `-O2`

```
gcc -O0 -S -masm=intel operations.c -o operations_O0.s
gcc -O2 -S -masm=intel operations.c -o operations_O2.s
diff -u operations_O0.s operations_O2.s
```

`calculate` на `-O2`:

```asm
calculate:
    endbr64
    lea     eax, [rdi+rsi]
    ret
```

`main` на `-O2`:

```asm
main:
    endbr64
    sub     rsp, 8
    mov     edx, 30             ; ← готове значення!
    mov     edi, 2
    xor     eax, eax
    lea     rsi, .LC0[rip]
    call    __printf_chk@PLT
    xor     eax, eax
    add     rsp, 8
    ret
```

| | `-O0` | `-O2` |
|---|---|---|
| інструкцій у `calculate` | 12 | 3 (`endbr64`, `lea`, `ret`) |
| рядків у `.s` файлі | 78 | 58 |
| `call calculate` у `main` | є | **немає** |
| як рахується 10 + 20 | під час виконання | під час компіляції, у коді просто `30` |

Що зробив компілятор на `-O2`:
- прибрав змінну `result` та роботу зі стеком (`push rbp`, `mov [rbp-..]`) — усе тримається в регістрах;
- додавання зробив через `lea eax, [rdi+rsi]` (це теж додавання двох регістрів, але однією інструкцією);
- вбудував `calculate` у `main` (inlining), і оскільки аргументи відомі (10 і 20), результат `30` порахував заздалегідь;
- замість `mov eax, 0` пише `xor eax, eax` (коротша інструкція з тим самим результатом);
- `printf` замінив на `__printf_chk` (версія з перевіркою, так налаштований Ubuntu).

Для інших функцій теж помітно: `max_value` на `-O2` став взагалі без переходів (`cmp` + `cmovge`), а цикл у `sum_to` перебудований так, що за один прохід додає два числа (`add eax, 2`). Висновок: **C-код не має єдиного Assembly**, результат залежить від налаштувань компілятора.

## Завдання 9. Прогноз для `10 + 20`

**Мій прогноз:** варіант B. Обидва числа відомі ще до запуску, тож компілятор може одразу покласти `30`.

```
gcc -O0 -S -masm=intel optimize.c -o optimize_O0.s
gcc -O2 -S -masm=intel optimize.c -o optimize_O2.s
```

`-O0`:

```asm
answer:
    endbr64
    push    rbp
    mov     rbp, rsp
    mov     eax, 30
    pop     rbp
    ret
main:
    ...
    call    answer
    ...
```

`-O2`:

```asm
answer:
    endbr64
    mov     eax, 30
    ret
main:
    endbr64
    mov     eax, 30       ; answer() узагалі не викликається
    ret
```

Прогноз підтвердився, і навіть сильніше: `30` з'являється вже на `-O0` (константний вираз GCC порахував ще при компіляції), а на `-O2` ще й зникає виклик `answer`, `main` одразу повертає 30. Окремої інструкції `add` для `10 + 20` немає ні в одному варіанті.

**Чому компілятор має на це право?**
Бо правило просте: програма має поводитись так само, як описано в C (результат, виведення), а як саме це досягнуто — справа компілятора. `10 + 20` завжди дорівнює 30, побічних ефектів у цьому виразі немає, тож рахувати його щоразу під час роботи програми немає сенсу.

## Фінальне завдання. `analyze.c`

Функція `mul_by_add(int a, int b)`: визначає більше й менше число (`if/else`), потім у циклі `for` додає більше число стільки разів, скільки «одиниць» у меншому (множення через додавання). `main` викликає `mul_by_add(6, 4)`.

```
gcc -Wall -Wextra -O0 analyze.c -o analyze && ./analyze
6 * 4 = 24

gcc -Wall -Wextra -O0 -S -masm=intel analyze.c -o analyze.s
objdump -d -M intel analyze
```

Змінні в пам'яті: `a` = `[rbp-0x14]`, `b` = `[rbp-0x18]`, `big` = `[rbp-0x10]`, `small` = `[rbp-0xc]`, `i` = `[rbp-0x4]`, `total` = `[rbp-0x8]`.

Фрагмент `<mul_by_add>` з `objdump`:

```
1161:  3b 45 e8             cmp    eax,DWORD PTR [rbp-0x18]
1164:  7e 0e                jle    1174 <mul_by_add+0x2b>
...
1189:  8b 45 f0             mov    eax,DWORD PTR [rbp-0x10]
118c:  01 45 f8             add    DWORD PTR [rbp-0x8],eax
118f:  83 45 fc 01          add    DWORD PTR [rbp-0x4],0x1
1193:  8b 45 fc             mov    eax,DWORD PTR [rbp-0x4]
1196:  3b 45 f4             cmp    eax,DWORD PTR [rbp-0xc]
1199:  7c ee                jl     1189 <mul_by_add+0x40>
119b:  8b 45 f8             mov    eax,DWORD PTR [rbp-0x8]
119e:  5d                   pop    rbp
119f:  c3                   ret
```

Що де знайшов:

| Що | Де |
|---|---|
| арифметична операція | `add DWORD PTR [rbp-0x8], eax` (0x118c) |
| comparison | `cmp eax, DWORD PTR [rbp-0x18]` (0x1161) для `if`, `cmp ... [rbp-0xc]` (0x1196) для циклу |
| conditional jump | `jle` (0x1164) для `if`, `jl` (0x1199) для циклу |
| цикл | блок `0x1189`–`0x1199`: тіло, `i++`, `cmp`, `jl` назад на `0x1189` |
| call | у `main`: `e8 8e ff ff ff` → `call 1149 <mul_by_add>` (0x11b6) |
| ret | `c3` за адресою 0x119f |

Три інструкції: C → Assembly → байти:

| C construct | Assembly | Address | Machine-code bytes |
|---|---|---|---|
| `total = total + big;` | `add DWORD PTR [rbp-0x8], eax` | 0x118c | `01 45 f8` |
| `if (a > b)` | `cmp eax, DWORD PTR [rbp-0x18]` | 0x1161 | `3b 45 e8` |
| `i < small` (умова циклу) | `jl 1189 <mul_by_add+0x40>` | 0x1199 | `7c ee` |

Звірка з `jl 7c ee`: `ee` як знакове число = −18, наступна інструкція стоїть за `0x119b`, `0x119b − 18 = 0x1189` — початок тіла циклу. Для `jle 7e 0e` на `0x1164`: `0x1166 + 14 = 0x1174` — гілка `else`. Бачимо, що умовні переходи теж кодуються «відстанню».

## Відповіді на контрольні питання

1. **Що таке ISA?** Instruction Set Architecture: набір інструкцій, регістрів та правил, які розуміє процесор (тут x86-64). Це «мова», яку CPU виконує.
2. **Чому CPU не виконує C напряму?** C-код — це текст для людини з іменами змінних, типами та циклами. Процесор виконує лише інструкції своєї ISA у вигляді байтів, тому код треба скомпілювати.
3. **Різниця між Assembly і machine code?** Machine code — самі байти (`01 d0`), які виконує CPU. Assembly — текстовий запис цих інструкцій (`add eax, edx`), що відповідає їм один до одного.
4. **Що робить `-S`?** Зупиняє GCC після генерації Assembly: створюється `.s` файл, а складання в object-файл і лінкування не відбуваються.
5. **Навіщо `-O0`?** Вимикає оптимізацію, тож Assembly близький до C-коду й його легше зіставляти з рядками.
6. **Що таке operand?** Те, над чим працює інструкція: регістр (`eax`), число (`5`) або місце в пам'яті (`DWORD PTR [rbp-4]`). У `add eax, edx` operand'ів два.
7. **Для чого `mov`?** Копіює значення: з пам'яті в регістр, з регістра в пам'ять, число в регістр. Ззовні назва «перемістити», але джерело залишається незмінним.
8. **Яку роль виконує `cmp`?** Порівнює два значення (віднімає, але результат не зберігає) і виставляє прапорці. Потім умовний перехід використовує ці прапорці.
9. **Як на машинному рівні реалізується `if`?** Через `cmp` та умовний перехід (`jle`, `jg`, `je`...) на мітку іншої гілки.
10. **Як реалізується цикл?** Через мітки, `cmp`, умовний перехід назад і `add` для зміни лічильника.
11. **Для чого `call`?** Викликає функцію: запам'ятовує адресу повернення й переходить до початку функції.
12. **Для чого `ret`?** Повертає керування на адресу, збережену при `call`, тобто в місце виклику.
13. **Чому одному рядку C не обов'язково відповідає одна інструкція?** Бо рядок може містити кілька дій (взяти значення, порахувати, записати), а процесор виконує прості кроки. `int result = a + b;` — це чотири інструкції.
14. **Що показує `objdump -d`?** Дизасемблювання виконуваного файлу: адреси, байти machine code та відповідні Assembly-інструкції.
15. **Чому `-O0` та `-O2` дають різний Assembly?** `-O2` дозволяє компілятору замінювати змінні регістрами, вбудовувати функції, рахувати константи наперед, змінювати порядок і навіть прибирати зайве (у нашому випадку `calculate` із 12 інструкцій стала 3, а виклик зник). Результат програми той самий.
16. **Чи може компілятор видалити частину C-коду?** Так, якщо це не змінює видиму поведінку програми (результат, виведення). Наприклад, обчислення, результат якого ніде не використовується, або код, що ніколи не виконається. Проте якщо код має ефект (друк, запис у `volatile`), його видаляти не можна.

## Короткий висновок

Експериментально встановлено:

- C-код перетворюється на Assembly (`-S`), а потім на байти machine code; у виконуваному файлі лежать саме байти, а `objdump` лише перекладає їх у читабельний вигляд;
- змінних з іменами в Assembly немає, є регістри та адреси в пам'яті; один рядок C — це зазвичай кілька інструкцій;
- арифметика — окремі інструкції (`add`, `sub`, `imul`), зміна оператора в C змінює саме її;
- `if` та цикли — це `cmp` плюс умовні переходи (`jle`, `jl`) та мітки, окремих інструкцій `IF` чи `for` не існує;
- `call` та `ret` реалізують виклик функції, і для повернення CPU мусить десь зберігати адресу — цим займемось у наступній роботі;
- інструкції x86-64 мають різну довжину (від 1 до 7 байтів у наших прикладах);
- оптимізація суттєво змінює код: на `-O2` `calculate` скоротилась з 12 до 3 інструкцій, а `10 + 20` було пораховано ще при компіляції. Тому Assembly залежить від компілятора та його налаштувань.

Відтворити все можна командами `gcc -S -masm=intel`, `objdump -d -M intel` та `diff -u` з цього README.


</details>
