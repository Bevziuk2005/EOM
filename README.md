## Завдання 1. Розміри типів

| Тип | Розмір, bytes | Розмір, bits |
|-----|:---:|:---:|
| char | 1 | 8 |
| short | 2 | 16 |
| int | 4 | 32 |
| long | 8 | 64 |
| long long | 8 | 64 |
| float | 4 | 32 |
| double | 8 | 64 |
| void * | 8 | 64 |

**Чи всі типи займають однакову кількість пам'яті?**
Ні. Від 1 байта (`char`) до 8 байтів (`long`, `double`, вказівник).

**Скільки бітів займає `int`?**
32 біти (4 байти).

**Який розмір має `void *`?**
8 байтів.

**Що це говорить про архітектуру?**
Вказівник зберігає адресу, тому його розмір відповідає розміру адреси на машині. 8 байтів = 64 біти, отже середовище 64-бітне (x86-64). Це збігається з `uname -m`.

Ще помітив, що `long` тут 8 байтів, хоча `int` лише 4. Тобто розмір типів залежить від платформи, а в стандарті C гарантовано тільки `sizeof(char) == 1`.

## Завдання 2. Decimal → Hexadecimal

| Decimal | Hexadecimal | Binary |
|--------:|:-----------:|:------:|
| 10 | 0xA | 1010 |
| 65 | 0x41 | 1000001 |
| 127 | 0x7F | 1111111 |
| 255 | 0xFF | 11111111 |
| 256 | 0x100 | 100000000 |
| 1024 | 0x400 | 10000000000 |

(спочатку розраховував вручну, потім звірив з виводом програми — збіглось)

**Чому `65`, `0x41` і `01000001` — це те саме значення?**
Це три способи записати одне число, як «сорок п'ять» і «45». У пам'яті лежить один і той самий набір бітів. Система числення — це лише наш спосіб його показати:
- decimal: 6·10 + 5 = 65
- hex: 4·16 + 1 = 65
- binary: 64 + 1 = 65

Hex зручний ще й тому, що одна шістнадцяткова цифра рівно відповідає 4 бітам, тож байт — це завжди дві hex-цифри (`0100 0001` → `4` і `1`).

## Завдання 3. Виведення бітів

Функція `print_binary(unsigned char value)` в `binary.c`. Результати:

| Decimal | Hex | Binary |
|--------:|:---:|:------:|
| 0 | 0x00 | 00000000 |
| 1 | 0x01 | 00000001 |
| 10 | 0x0A | 00001010 |
| 65 | 0x41 | 01000001 |
| 127 | 0x7F | 01111111 |
| 128 | 0x80 | 10000000 |
| 255 | 0xFF | 11111111 |

**Чому перевірка починається з біта 7, а не з біта 0?**
Біт 7 — старший. Числа ми читаємо зліва направо, від старшого розряду до молодшого, так само як `65` — спочатку десятки, потім одиниці. Якщо йти від біта 0, число вийде записане задом наперед (для 65 було б `10000010`).

## Завдання 4. Символ — це також число

| Character | Decimal | Hex |
|:---------:|--------:|:---:|
| A | 65 | 0x41 |
| B | 66 | 0x42 |
| a | 97 | 0x61 |
| 0 | 48 | 0x30 |
| 9 | 57 | 0x39 |

**Що зберігається в `char c = 'A';`?**
Число 65 (один байт `01000001`). Літери як такої в пам'яті немає. Коли `printf` отримує `%c`, він бере це число й за таблицею ASCII малює символ `A`; коли отримує `%d`, то просто друкує число. Підтвердження — вираз `'A' + 1` дає 66, тобто `'B'`.

Також цікаво: символ `'0'` — це не число 0, а код 48. Цифра-символ і цифра-число — різні речі.

## Завдання 5. Signed та Unsigned

**Прогноз до запуску:** для `-1` у `int8_t` очікую `11111111`. Логіка: у two's complement мінус одиниця — це «усі біти одиниці» (інвертуємо `00000001` → `11111110` і додаємо 1 → `11111111`).

**Результат:**

```
int8_t  = -1
uint8_t = 255

int8_t  (-1)  hex: 0xFF  bits: 11111111
uint8_t (255) hex: 0xFF  bits: 11111111
```

Прогноз підтвердився: біти в обох змінних однакові.

**Як `11111111` може бути і 255, і -1?**
Біти однакові, відрізняється правило, за яким їх читають. Для `uint8_t` усі 8 бітів — це величина: 128+64+32+16+8+4+2+1 = 255. Для `int8_t` старший біт має вагу −128, тому: −128 + 127 = −1. Значення визначає **тип**, а не самі біти.

---

## Завдання 6. Межа unsigned integer

**Прогноз до запуску:** `255 + 1` у `uint8_t` дасть `0`. У байті лише 8 бітів, результат 256 = `1 0000 0000` потребує дев'ятого біта, якого немає, тож він відкидається і залишається `00000000`.

Під час обчислення `a + 1` значення `a` спочатку підвищується до `int` (integer promotion), тому вираз розраховується як `256`, а потім результат зберігається в `uint8_t`, де він обгортається за модулем 256.

**Результат:**

```
Before: 255
After value++: 0

254         -> 254
255         -> 255
255 + 1     -> 0
255 + 2     -> 1
```

Прогноз підтвердився. Фактично `uint8_t` рахує за модулем 256: після 255 знову 0, потім 1 і так по колу.

Для `uint8_t` діапазон 0…255 (2⁸ значень), і при переході через верхню межу відбувається «обгортання». Цю поведінку я перевіряв саме для беззнакового типу. На знакові типи її переносити не можна: у C signed overflow — це undefined behavior, там компілятор нічого не гарантує.

## Завдання 7–8. Пам'ять та endianness

**Гіпотеза до запуску:** число `0x12345678` займає 4 байти. На x86 я очікую варіант **B**, тобто `78 56 34 12` (молодший байт за найменшою адресою), бо це має бути little-endian.

**Фактичний результат:**

```
value = 0x12345678

byte 0 = 0x78
byte 1 = 0x56
byte 2 = 0x34
byte 3 = 0x12

Address              Value
0x7ffff5824984       0x78
0x7ffff5824985       0x56
0x7ffff5824986       0x34
0x7ffff5824987       0x12
```

Гіпотеза підтвердилась: варіант B.

**У якому напрямку змінюються адреси?**
Зростають: `...764` → `...765` → `...766` → `...767` (кожна на 1 байт більша).

**Який байт лежить за найменшою адресою?**
`0x78` — молодший байт числа.

**Чому це little-endian?**
Бо молодший байт стоїть першим, за найменшою адресою, а старший `0x12` — останнім. У big-endian було б навпаки: `12 34 56 78`.

**Чи змінилось саме число?**
Ні. Значення залишається `0x12345678`, коли ми читаємо його як `uint32_t`. Змінюється лише те, як байти розкладені в пам'яті. Тому порядок байтів важливо враховувати, коли дивимось на пам'ять побайтово (мережеві протоколи, файли, дампи).

---

## Завдання 9. Одні біти — різні інтерпретації

| Інтерпретація | Значення |
|---------------|----------|
| Binary | 01000001 |
| Hexadecimal | 0x41 |
| Unsigned decimal | 65 |
| ASCII character | A |

**Чому комп'ютеру недостатньо знати лише біти?**
Бо біти самі по собі нічого не означають. Той самий байт `01000001` — це і число 65, і літера `A`, і частина адреси чи кольору. Щоб отримати значення, потрібні **тип** (`uint8_t`, `int8_t`, `char`...), що задає правило **інтерпретації**, і **контекст** (як програма це використовує і яким форматом ми це виводимо). Без типу й контексту `11111111` може бути 255, −1 чи просто «усі біти увімкнено».

## Відповіді на контрольні питання

1. **Що таке біт і байт?** Біт — найменша одиниця інформації, 0 або 1. Байт — 8 бітів, найменша адресована одиниця пам'яті.
2. **Скільки значень можна представити за допомогою n бітів?** 2ⁿ.
3. **Діапазон 8-бітного unsigned:** 0…255.
4. **Діапазон 8-бітного signed (two's complement):** −128…127.
5. **Чому hex зручний?** Одна hex-цифра = 4 біти, байт = 2 цифри. Запис короткий, а перетворення в біти й назад майже миттєве.
6. **Чим відрізняється `11111111` як `uint8_t` та `int8_t`?** Біти ті самі; як `uint8_t` це 255, як `int8_t` це −1.
7. **Що буде після збільшення `uint8_t` зі значенням 255?** Стане 0 (обгортання за модулем 256).
8. **Що зберігається в пам'яті для символу `A`?** Число 65 (`0x41`, `01000001`).
9. **Що таке endianness?** Порядок, у якому байти багатобайтового значення розташовані в пам'яті.
10. **Який порядок на досліджуваній x86-64 системі?** Little-endian.
11. **Що означає `sizeof(int)`?** Розмір типу `int` у байтах для поточного компілятора і платформи (тут 4).
12. **Чому одні й ті самі біти можуть представляти різні дані?** Бо їхнє значення задається типом та контекстом, а не самими бітами.

---

## Короткий підсумок

Експериментально встановлено:

- на цій системі `int` = 4 байти, `long` і `void *` = 8 байтів, отже середовище 64-бітне;
- 65, `0x41` і `01000001` — один і той самий байт у різних записах;
- символ у C — це число (`'A'` = 65), літерою його робить лише виведення;
- `11111111` читається як 255 (`uint8_t`) або −1 (`int8_t`), залежно від типу;
- `uint8_t` після 255 переходить у 0, бо для результату просто немає 9-го біта;
- на x86-64 байти зберігаються за схемою little-endian: у `0x12345678` за найменшою адресою лежить `0x78`.

Головний висновок: пам'ять зберігає лише біти, а їхній сенс задають тип і спосіб інтерпретації.

## Підготовка. `arithmetic.c`

## Завдання 1. Отримуємо Assembly

```
gcc -Wall -Wextra -O0 -S -masm=intel arithmetic.c -o arithmetic_intel.s
```

Тіло `main` (без службових директив `.cfi`):

```asm
main:
    endbr64
    push    rbp
    mov     rbp, rsp
    sub     rsp, 16
    mov     DWORD PTR -12[rbp], 5        ; a = 5
    mov     DWORD PTR -8[rbp], 7         ; b = 7
    mov     edx, DWORD PTR -12[rbp]      ; edx = a
    mov     eax, DWORD PTR -8[rbp]       ; eax = b
    add     eax, edx                     ; eax = a + b
    mov     DWORD PTR -4[rbp], eax       ; result = eax
    mov     eax, DWORD PTR -4[rbp]
    mov     esi, eax                     ; 2-й аргумент printf
    lea     rax, .LC0[rip]               ; адреса рядка "Result: %d\n"
    mov     rdi, rax                     ; 1-й аргумент printf
    mov     eax, 0
    call    printf@PLT
    mov     eax, 0                       ; return 0
    leave
    ret
```

Знайшов:
- функція `main` — мітка `main:`;
- `mov` — багато разів (пересилання значень);
- додавання — `add eax, edx`;
- виклик `printf` — `call printf@PLT`;
- `ret` в кінці.

**Чи кожному рядку C відповідає рівно одна інструкція?**
Ні. Рядок `int result = a + b;` перетворився на чотири інструкції (`mov`, `mov`, `add`, `mov`), а `printf(...)` — на цілу групу (підготувати аргументи + `call`).

**Чи є в Assembly змінні `a`, `b`, `result`?**
Ні, імен немає. Є лише місця в пам'яті відносно `rbp`: `a` лежить за `[rbp-12]`, `b` за `[rbp-8]`, `result` за `[rbp-4]`. Імена змінних потрібні людині та компілятору, процесору вони не потрібні.

**Скільки інструкцій у `main()`?**
Від `endbr64` до `ret` вийшло 19 інструкцій, при тому що в тілі `main` усього 5 рядків C.

**Чи є додавання?**
Так, `add eax, edx`.

## Завдання 2. Арифметична операція

`operations.c` працює і виводить `30`. Функція `calculate` в Assembly:

```asm
calculate:
    endbr64
    push    rbp
    mov     rbp, rsp
    mov     DWORD PTR -20[rbp], edi      ; параметр a прийшов у edi
    mov     DWORD PTR -24[rbp], esi      ; параметр b прийшов у esi
    mov     edx, DWORD PTR -20[rbp]
    mov     eax, DWORD PTR -24[rbp]
    add     eax, edx                     ; a + b
    mov     DWORD PTR -4[rbp], eax       ; result
    mov     eax, DWORD PTR -4[rbp]       ; готуємо значення для повернення
    pop     rbp
    ret
```

Регістри: `edi` і `esi` — аргументи функції (перший і другий), `eax` — тут рахується сума й одночасно звідти повертається результат, `edx` — допоміжний.

**Експеримент.** Підміняв рядок з обчисленням на `a + b`, `a - b`, `a * b`, щоразу збирав `-O0 -S -masm=intel`:

| C | Основна Assembly-інструкція | Як виглядає |
|---|---|---|
| `a + b` | `add` | `add eax, edx` |
| `a - b` | `sub` | `sub eax, DWORD PTR -24[rbp]` |
| `a * b` | `imul` | `imul eax, DWORD PTR -24[rbp]` |

**Що змінилось після заміни однієї операції?**
Практично тільки одна інструкція: `add` → `sub` → `imul`. Решта (збереження аргументів, `push rbp`, повернення через `eax`, `ret`) залишилась такою самою. Для `-` і `*` компілятор ще й одразу бере другий операнд із пам'яті, тому зникла окрема пара `mov edx...`/`mov eax...`. Тобто змінюючи оператор у C, ми змінюємо саме арифметичну інструкцію.

## Завдання 3. `if`

`condition.c` працює і виводить `20`. Функція `max_value`:

```asm
max_value:
    endbr64
    push    rbp
    mov     rbp, rsp
    mov     DWORD PTR -4[rbp], edi       ; a
    mov     DWORD PTR -8[rbp], esi       ; b
    mov     eax, DWORD PTR -4[rbp]       ; eax = a
    cmp     eax, DWORD PTR -8[rbp]       ; порівняти a і b
    jle     .L2                          ; якщо a <= b — стрибок на else
    mov     eax, DWORD PTR -4[rbp]       ; return a
    jmp     .L3                          ; пропустити else
.L2:
    mov     eax, DWORD PTR -8[rbp]       ; return b
.L3:
    pop     rbp
    ret
```

Відповідність:

```
C                       Assembly

if (a > b)        →     mov eax, [a]
                        cmp eax, [b]
                        jle .L2          (стрибок, якщо умова НЕ виконана)

return a          →     mov eax, [a]
                        jmp .L3

else              →     мітка .L2:

return b          →     mov eax, [b]     (далі .L3: pop rbp / ret)
```

Цікаво, що компілятор «перевернув» умову: у C написано `a > b`, а стрибок стоїть на протилежну `jle`. Логіка така: якщо умова хибна, перестрибуємо на `else`, а якщо істинна, просто йдемо далі по рядках.

**Чи існує машинна інструкція `IF` у тому сенсі, як у C?**
Ні. CPU реалізує `if` двома кроками: `cmp` порівнює числа й записує результат у регістр прапорців (flags), а потім умовний перехід (`jle`, `jg`, `je`...) дивиться на ці прапорці. Якщо умова спрацювала, процесор змінює адресу наступної інструкції (стрибок), а якщо ні — виконує наступну по порядку. Дві гілки — це просто два шматки коду з мітками.

## Завдання 4. Цикл

`loop.c` працює і виводить `15`. Функція `sum_to`:

```asm
sum_to:
    endbr64
    push    rbp
    mov     rbp, rsp
    mov     DWORD PTR -20[rbp], edi      ; n
    mov     DWORD PTR -8[rbp], 0         ; sum = 0
    mov     DWORD PTR -4[rbp], 1         ; i = 1          (initialization)
    jmp     .L2                          ; одразу до перевірки умови
.L3:
    mov     eax, DWORD PTR -4[rbp]       ;                (body)
    add     DWORD PTR -8[rbp], eax       ; sum += i
    add     DWORD PTR -4[rbp], 1         ; i++            (increment)
.L2:
    mov     eax, DWORD PTR -4[rbp]
    cmp     eax, DWORD PTR -20[rbp]      ; i порівнюється з n   (condition)
    jle     .L3                          ; i <= n — стрибок назад на тіло
    mov     eax, DWORD PTR -8[rbp]       ; return sum
    pop     rbp
    ret
```

Структура цикла в Assembly:

```
i = 1                 →  mov [i], 1
перехід до умови      →  jmp .L2
.L2: умова            →  mov eax,[i] ; cmp eax,[n] ; jle .L3
.L3: тіло             →  add [sum], eax
зміна i               →  add [i], 1
стрибок назад         →  (знову .L2 → jle .L3)
вихід з циклу         →  інструкція після jle
```

Умова стоїть **після** тіла: на початку компілятор один раз стрибає на неї (`jmp .L2`), а далі умова працює як «перевірка в кінці кожного кола».

**Яка інструкція виконує порівняння?** `cmp eax, DWORD PTR -20[rbp]`.
**Яка інструкція реалізує перехід?** `jle .L3` — умовний перехід назад (і `jmp .L2` — безумовний, на самому початку).
**Чи існує в Assembly поняття `for`?** Ні, воно розкладене на `mov` (ініціалізація), `cmp`, умовний перехід, тіло, `add` (зміна `i`) і стрибок назад.
**Як CPU вирішує, що цикл треба повторити?** `cmp` виставляє прапорці за результатом порівняння `i` та `n`; `jle` дивиться на прапорці. Поки `i <= n`, стрибок виконується й керування йде на початок тіла; коли `i` стає більшим за `n`, стрибок не спрацьовує й виконується наступна інструкція після циклу.

## Завдання 5. Виклик функції

З `main` у `operations.c` (bytes та адреси — з `objdump`, див. нижче):

```asm
main:
    ...
    mov     esi, 20            ; другий аргумент
    mov     edi, 10            ; перший аргумент
    call    calculate          ; ← виклик
    mov     DWORD PTR -4[rbp], eax   ; результат повернувся в eax
```

- виклик `calculate` — `call` за адресою `0x117d`;
- код `calculate` починається за адресою `0x1149`;
- функція завершується інструкцією `ret` за адресою `0x1166`;
- результат повертається в регістрі `eax`.

**Чому після `call` CPU повинен знати, куди повертатись?**
Бо `calculate` можна викликати з будь-якого місця програми, і після `ret` треба продовжити саме там, де зупинились. Тому `call` перед стрибком запам'ятовує адресу наступної інструкції (тут `0x1182`), а `ret` дістає її й повертається. Де саме ця адреса зберігається — тема наступної лабораторної (стек).

## Завдання 6–7. Machine code

```
gcc -Wall -Wextra -O0 operations.c -o operations
```

Фрагмент `<calculate>`:

```

    1154:  89 75 e8              mov    DWORD PTR [rbp-0x18],esi
    1157:  8b 55 ec              mov    edx,DWORD PTR [rbp-0x14]

    115d:  01 d0                 add    eax,edx
    115f:  89 45 fc              mov    DWORD PTR [rbp-0x4],eax
    1162:  8b 45 fc              mov    eax,DWORD PTR [rbp-0x4]
    1165:  5d                    pop    rbp

```

Три інструкції з реального файлу:

| Address | Machine-code bytes | Assembly |
|---------|--------------------|----------|
| 0x115d | `01 d0` | `add eax, edx` |
| 0x117d | `e8 c7 ff ff ff` | `call 1149 <calculate>` |
| 0x1166 | `c3` | `ret` |

Перевірив `call` руками: байти `c7 ff ff ff` — це число `0xffffffc7` = −57 (байти йдуть у little-endian, як у лабораторній 1). Наступна інструкція стоїть за адресою `0x1182`, і `0x1182 − 57 = 0x1149` — це якраз початок `calculate`. Тобто `call` зберігає не абсолютну адресу, а відстань до функції.

**Що зберігається у виконуваному файлі: текст Assembly чи machine code?**
Machine code, тобто байти. Тексту `add eax, edx` там немає.

**Навіщо тоді `objdump` показує Assembly?**
Це дизасемблер: він читає байти й перекладає їх назад у мнемоніки, щоб людина могла це прочитати. `01 d0` ↔ `add eax, edx` — це два записи однієї інструкції.

**Чи всі інструкції x86-64 мають однакову довжину?**
Ні. У цьому файлі є й 1 байт (`c3`, `55`), й 2 (`01 d0`), 3 (`48 89 e5`), 4 (`f3 0f 1e fa`), 5 (`e8 ...`), 7 (`48 8d 05 73 0e 00 00` — `lea rax, [rip+0xe73]` в `main`).

**Чому людині зручніше читати Assembly?**
Мнемоніки (`add`, `mov`, `call`) легше запам'ятати й зрозуміти, ніж шістнадцяткові байти, а адреси переходів і імена функцій `objdump` підставляє сам.

## Завдання 8. Оптимізація: `-O0` проти `-O2`

```
gcc -O0 -S -masm=intel operations.c -o operations_O0.s
gcc -O2 -S -masm=intel operations.c -o operations_O2.s
diff -u operations_O0.s operations_O2.s
```

`calculate` на `-O2`:

```asm
calculate:
    endbr64
    lea     eax, [rdi+rsi]
    ret
```

`main` на `-O2`:

```asm
main:
    endbr64
    sub     rsp, 8
    mov     edx, 30             ; ← готове значення!
    mov     edi, 2
    xor     eax, eax
    lea     rsi, .LC0[rip]
    call    __printf_chk@PLT
    xor     eax, eax
    add     rsp, 8
    ret
```

| | `-O0` | `-O2` |
|---|---|---|
| інструкцій у `calculate` | 12 | 3 (`endbr64`, `lea`, `ret`) |
| рядків у `.s` файлі | 78 | 58 |
| `call calculate` у `main` | є | **немає** |
| як рахується 10 + 20 | під час виконання | під час компіляції, у коді просто `30` |

Що зробив компілятор на `-O2`:
- прибрав змінну `result` та роботу зі стеком (`push rbp`, `mov [rbp-..]`) — усе тримається в регістрах;
- додавання зробив через `lea eax, [rdi+rsi]` (це теж додавання двох регістрів, але однією інструкцією);
- вбудував `calculate` у `main` (inlining), і оскільки аргументи відомі (10 і 20), результат `30` порахував заздалегідь;
- замість `mov eax, 0` пише `xor eax, eax` (коротша інструкція з тим самим результатом);
- `printf` замінив на `__printf_chk` (версія з перевіркою, так налаштований Ubuntu).

Для інших функцій теж помітно: `max_value` на `-O2` став взагалі без переходів (`cmp` + `cmovge`), а цикл у `sum_to` перебудований так, що за один прохід додає два числа (`add eax, 2`). Висновок: **C-код не має єдиного Assembly**, результат залежить від налаштувань компілятора.

## Завдання 9. Прогноз для `10 + 20`

**Мій прогноз:** варіант B. Обидва числа відомі ще до запуску, тож компілятор може одразу покласти `30`.

```
gcc -O0 -S -masm=intel optimize.c -o optimize_O0.s
gcc -O2 -S -masm=intel optimize.c -o optimize_O2.s
```

`-O0`:

```asm
answer:
    endbr64
    push    rbp
    mov     rbp, rsp
    mov     eax, 30
    pop     rbp
    ret
main:
    ...
    call    answer
    ...
```

`-O2`:

```asm
answer:
    endbr64
    mov     eax, 30
    ret
main:
    endbr64
    mov     eax, 30       ; answer() узагалі не викликається
    ret
```

Прогноз підтвердився, і навіть сильніше: `30` з'являється вже на `-O0` (константний вираз GCC порахував ще при компіляції), а на `-O2` ще й зникає виклик `answer`, `main` одразу повертає 30. Окремої інструкції `add` для `10 + 20` немає ні в одному варіанті.

**Чому компілятор має на це право?**
Бо правило просте: програма має поводитись так само, як описано в C (результат, виведення), а як саме це досягнуто — справа компілятора. `10 + 20` завжди дорівнює 30, побічних ефектів у цьому виразі немає, тож рахувати його щоразу під час роботи програми немає сенсу.

## Фінальне завдання. `analyze.c`

Функція `mul_by_add(int a, int b)`: визначає більше й менше число (`if/else`), потім у циклі `for` додає більше число стільки разів, скільки «одиниць» у меншому (множення через додавання). `main` викликає `mul_by_add(6, 4)`.

```
gcc -Wall -Wextra -O0 analyze.c -o analyze && ./analyze
6 * 4 = 24

gcc -Wall -Wextra -O0 -S -masm=intel analyze.c -o analyze.s
objdump -d -M intel analyze
```

Змінні в пам'яті: `a` = `[rbp-0x14]`, `b` = `[rbp-0x18]`, `big` = `[rbp-0x10]`, `small` = `[rbp-0xc]`, `i` = `[rbp-0x4]`, `total` = `[rbp-0x8]`.

Фрагмент `<mul_by_add>` з `objdump`:

```
1161:  3b 45 e8             cmp    eax,DWORD PTR [rbp-0x18]
1164:  7e 0e                jle    1174 <mul_by_add+0x2b>
...
1189:  8b 45 f0             mov    eax,DWORD PTR [rbp-0x10]
118c:  01 45 f8             add    DWORD PTR [rbp-0x8],eax
118f:  83 45 fc 01          add    DWORD PTR [rbp-0x4],0x1
1193:  8b 45 fc             mov    eax,DWORD PTR [rbp-0x4]
1196:  3b 45 f4             cmp    eax,DWORD PTR [rbp-0xc]
1199:  7c ee                jl     1189 <mul_by_add+0x40>
119b:  8b 45 f8             mov    eax,DWORD PTR [rbp-0x8]
119e:  5d                   pop    rbp
119f:  c3                   ret
```

Що де знайшов:

| Що | Де |
|---|---|
| арифметична операція | `add DWORD PTR [rbp-0x8], eax` (0x118c) |
| comparison | `cmp eax, DWORD PTR [rbp-0x18]` (0x1161) для `if`, `cmp ... [rbp-0xc]` (0x1196) для циклу |
| conditional jump | `jle` (0x1164) для `if`, `jl` (0x1199) для циклу |
| цикл | блок `0x1189`–`0x1199`: тіло, `i++`, `cmp`, `jl` назад на `0x1189` |
| call | у `main`: `e8 8e ff ff ff` → `call 1149 <mul_by_add>` (0x11b6) |
| ret | `c3` за адресою 0x119f |

Три інструкції: C → Assembly → байти:

| C construct | Assembly | Address | Machine-code bytes |
|---|---|---|---|
| `total = total + big;` | `add DWORD PTR [rbp-0x8], eax` | 0x118c | `01 45 f8` |
| `if (a > b)` | `cmp eax, DWORD PTR [rbp-0x18]` | 0x1161 | `3b 45 e8` |
| `i < small` (умова циклу) | `jl 1189 <mul_by_add+0x40>` | 0x1199 | `7c ee` |

Звірка з `jl 7c ee`: `ee` як знакове число = −18, наступна інструкція стоїть за `0x119b`, `0x119b − 18 = 0x1189` — початок тіла циклу. Для `jle 7e 0e` на `0x1164`: `0x1166 + 14 = 0x1174` — гілка `else`. Бачимо, що умовні переходи теж кодуються «відстанню».

## Відповіді на контрольні питання

1. **Що таке ISA?** Instruction Set Architecture: набір інструкцій, регістрів та правил, які розуміє процесор (тут x86-64). Це «мова», яку CPU виконує.
2. **Чому CPU не виконує C напряму?** C-код — це текст для людини з іменами змінних, типами та циклами. Процесор виконує лише інструкції своєї ISA у вигляді байтів, тому код треба скомпілювати.
3. **Різниця між Assembly і machine code?** Machine code — самі байти (`01 d0`), які виконує CPU. Assembly — текстовий запис цих інструкцій (`add eax, edx`), що відповідає їм один до одного.
4. **Що робить `-S`?** Зупиняє GCC після генерації Assembly: створюється `.s` файл, а складання в object-файл і лінкування не відбуваються.
5. **Навіщо `-O0`?** Вимикає оптимізацію, тож Assembly близький до C-коду й його легше зіставляти з рядками.
6. **Що таке operand?** Те, над чим працює інструкція: регістр (`eax`), число (`5`) або місце в пам'яті (`DWORD PTR [rbp-4]`). У `add eax, edx` operand'ів два.
7. **Для чого `mov`?** Копіює значення: з пам'яті в регістр, з регістра в пам'ять, число в регістр. Ззовні назва «перемістити», але джерело залишається незмінним.
8. **Яку роль виконує `cmp`?** Порівнює два значення (віднімає, але результат не зберігає) і виставляє прапорці. Потім умовний перехід використовує ці прапорці.
9. **Як на машинному рівні реалізується `if`?** Через `cmp` та умовний перехід (`jle`, `jg`, `je`...) на мітку іншої гілки.
10. **Як реалізується цикл?** Через мітки, `cmp`, умовний перехід назад і `add` для зміни лічильника.
11. **Для чого `call`?** Викликає функцію: запам'ятовує адресу повернення й переходить до початку функції.
12. **Для чого `ret`?** Повертає керування на адресу, збережену при `call`, тобто в місце виклику.
13. **Чому одному рядку C не обов'язково відповідає одна інструкція?** Бо рядок може містити кілька дій (взяти значення, порахувати, записати), а процесор виконує прості кроки. `int result = a + b;` — це чотири інструкції.
14. **Що показує `objdump -d`?** Дизасемблювання виконуваного файлу: адреси, байти machine code та відповідні Assembly-інструкції.
15. **Чому `-O0` та `-O2` дають різний Assembly?** `-O2` дозволяє компілятору замінювати змінні регістрами, вбудовувати функції, рахувати константи наперед, змінювати порядок і навіть прибирати зайве (у нашому випадку `calculate` із 12 інструкцій стала 3, а виклик зник). Результат програми той самий.
16. **Чи може компілятор видалити частину C-коду?** Так, якщо це не змінює видиму поведінку програми (результат, виведення). Наприклад, обчислення, результат якого ніде не використовується, або код, що ніколи не виконається. Проте якщо код має ефект (друк, запис у `volatile`), його видаляти не можна.

## Короткий висновок

Експериментально встановлено:

- C-код перетворюється на Assembly (`-S`), а потім на байти machine code; у виконуваному файлі лежать саме байти, а `objdump` лише перекладає їх у читабельний вигляд;
- змінних з іменами в Assembly немає, є регістри та адреси в пам'яті; один рядок C — це зазвичай кілька інструкцій;
- арифметика — окремі інструкції (`add`, `sub`, `imul`), зміна оператора в C змінює саме її;
- `if` та цикли — це `cmp` плюс умовні переходи (`jle`, `jl`) та мітки, окремих інструкцій `IF` чи `for` не існує;
- `call` та `ret` реалізують виклик функції, і для повернення CPU мусить десь зберігати адресу — цим займемось у наступній роботі;
- інструкції x86-64 мають різну довжину (від 1 до 7 байтів у наших прикладах);
- оптимізація суттєво змінює код: на `-O2` `calculate` скоротилась з 12 до 3 інструкцій, а `10 + 20` було пораховано ще при компіляції. Тому Assembly залежить від компілятора та його налаштувань.

Відтворити все можна командами `gcc -S -masm=intel`, `objdump -d -M intel` та `diff -u` з цього README.

</details>

## 1. Preprocessing

```
gcc -E program.c -o program.i
file program.i
wc -l program.c program.i
grep -n "int main" program.i
```

```
program.c: C source, ASCII text
program.i: C source, ASCII text

   17 program.c
  830 program.i
```

`int main` у `program.i` знайшовся на 824-му рядку, тобто наш код опинився в самому кінці файлу.

Початок `program.i` — службові позначки (`# 1 "program.c"`, `# 1 "/usr/include/stdc-predef.h"` та інші), далі йде вміст заголовків. Серед них є й оголошення, яке нам потрібне:

```
476: extern int printf (const char *__restrict __format, ...);
```

**Чому `program.i` значно більший за `program.c`?**
Бо preprocessor замінив `#include <stdio.h>` на повний текст `stdio.h` та усіх заголовків, які він підключає: типи, константи, оголошення функцій. Так 17 рядків стали 830.

**Що сталося з `#include <stdio.h>`?**
Самого рядка в `.i` уже немає, замість нього лежить вміст файла.

**Чи є `program.i` машинним кодом? Чи може CPU його виконати?**
Ні. `file` показує `C source, ASCII text`: це все ще звичайний C-текст, лише директиви preprocessing вже оброблені.

## 2. Compilation: `.i` → `.s`

```
gcc -S -O0 -masm=intel program.i -o program.s
file program.s
```

```
program.s: assembler source, ASCII text
```

Функції `add` та `main` в Assembly:

```asm
add:
    endbr64
    push    rbp
    mov     rbp, rsp
    mov     DWORD PTR -4[rbp], edi
    mov     DWORD PTR -8[rbp], esi
    mov     edx, DWORD PTR -4[rbp]
    mov     eax, DWORD PTR -8[rbp]
    add     eax, edx                      ; ← return a + b
    pop     rbp
    ret

main:
    endbr64
    push    rbp
    mov     rbp, rsp
    sub     rsp, 16
    mov     eax, DWORD PTR global_value[rip]   ; global_value
    mov     esi, 20
    mov     edi, eax
    call    add                                ; ← виклик add(global_value, 20)
    mov     DWORD PTR -4[rbp], eax
    mov     eax, DWORD PTR -4[rbp]
    mov     esi, eax
    lea     rax, .LC0[rip]                     ; адреса рядка "Result: %d\n"
    mov     rdi, rax
    mov     eax, 0
    call    printf@PLT
    mov     eax, 0
    leave
    ret
```

**Якою мовою представлений `program.s`?** Мовою Assembly x86-64 у текстовому вигляді (Intel syntax, бо `-masm=intel`; про це говорять регістри `rbp`, `eax` і директива `.intel_syntax noprefix`).
**Чи це machine code?** Ні, це текст. Machine code з'явиться після assembler.
**Для якої ISA?** x86-64.
**Чи видно `main` та `add`?** Так, це мітки `main:` та `add:`.

## 3. Assembly → Object file

```
gcc -c program.s -o program.o
file program.o
```

```
program.o: ELF 64-bit LSB relocatable, x86-64, version 1 (SYSV), not stripped
```

**Чому `cat program.o` виглядає зовсім інакше?**
Бо це двійковий файл, а не текст. Він починається з байтів `7f 45 4c 46 02 01 01 00 ...` (тобто `\x7f` і літери `ELF`), далі йдуть секції з машинним кодом, таблиця symbols та relocations. Термінал намагається показати це як символи й виводить сміття.

`objdump -d -M intel program.o` знову показує Assembly, але вже перекладений з байтів. Важливий фрагмент `main` (з relocations, `objdump -dr`):

```
0000000000000018 <main>:
  24:  8b 05 00 00 00 00     mov    eax,DWORD PTR [rip+0x0]
            26: R_X86_64_PC32   global_value-0x4
  31:  e8 00 00 00 00        call   36 <main+0x1e>
            32: R_X86_64_PLT32  add-0x4
  3e:  48 8d 05 00 00 00 00  lea    rax,[rip+0x0]
            41: R_X86_64_PC32   .rodata-0x4
  4d:  e8 00 00 00 00        call   52 <main+0x3a>
            4e: R_X86_64_PLT32  printf-0x4
```

Тут видно головне: у `.o` адреси в `call` та в посиланні на `global_value` — нулі (`00 00 00 00`), а поруч стоїть запис relocation: «сюди треба підставити адресу `add` / `printf` / `global_value`». Адреси ще невідомі, їх визначить linker.

Що зберігає кожен файл:

| File | Representation |
|---|---|
| `program.c` | текст на C, написаний людиною |
| `program.i` | текст на C після preprocessing (директиви оброблені) |
| `program.s` | текст на Assembly x86-64 |
| `program.o` | двійковий ELF relocatable: machine code + symbols + relocations |

## 4. Symbols

```
nm program.o
```

```
0000000000000000 T add
0000000000000000 B global_empty
0000000000000000 D global_value
0000000000000018 T main
                 U printf
```

Літери: `T` — функція визначена в цьому файлі (секція `.text`), `D` — змінна з початковим значенням (`.data`), `B` — змінна без значення (`.bss`), `U` — undefined, тобто символ потрібен, але визначений деінде.

**Чи є в `program.o` реалізація `add()`?** Так, `T add`.
**Реалізація `main()`?** Так, `T main`.
**Реалізація `printf()`?** Ні, лише `U printf`.
**Як програма зможе використати `printf()`?** Реалізація `printf` лежить у C library (`libc`). Її зв'язує linker: він знаходить `printf` у бібліотеці й підставляє адресу замість нулів у relocation.

## 5. Linking

```
gcc program.o -o program_from_object
file program_from_object
./program_from_object
```

```
program_from_object: ELF 64-bit LSB pie executable, x86-64, version 1 (SYSV), dynamically linked,
                     interpreter /lib64/ld-linux-x86-64.so.2, ... not stripped
Result: 30
```

Порівняння `file`: `program.o` — це `relocatable`, а `program` — `pie executable, dynamically linked` з `interpreter`, тобто він готовий до запуску й знає, що йому потрібен динамічний завантажувач.

Нулі в `call` лінкер замінив реальними числами. Приклад з `objdump -d program`:

```
117a:  e8 ca ff ff ff    call  1149 <add>
1196:  e8 b5 fe ff ff    call  1050 <printf@plt>
```

Для `call add` перевірка: `0xffffffca` = −54, наступна інструкція стоїть за `0x117f`, `0x117f − 54 = 0x1149` — адреса `add`. А `printf` викликається через таблицю `plt`, яку підготував linker для динамічного підключення.

Весь pipeline пройдено:
`program.c → program.i → program.s → program.o → program`.

## 6. Linker error та її виправлення

`main.c` лише оголошує `int calculate(int a, int b);`, але не реалізує її.

```
$ gcc -c main.c -o main.o
$                                      ← без помилок
$ gcc main.o -o app
/usr/bin/ld: main.o: in function `main':
main.c:(.text+0x17): undefined reference to `calculate'
collect2: error: ld returned 1 exit status
```

**Чому compilation пройшла, а linking — ні?**
Для компілятора досить оголошення: він знає ім'я, тип параметрів і результат, цього досить, щоб згенерувати `call`. Реалізації він не перевіряє. Linker же з'єднує файли й для кожного `U` символу шукає визначення. Для `calculate` його не знайшлось.

```
$ nm main.o
                 U calculate          ← main.o потребує calculate
0000000000000000 T main
                 U printf

$ gcc -c calculate.c -o calculate.o
$ nm calculate.o
0000000000000000 T calculate          ← calculate.o визначає calculate

$ gcc main.o calculate.o -o app && ./app
30
```

Виправлення: скомпілювати `calculate.c` в окремий object file та передати обидва `.o` linker'у. У `main.o` символ `calculate` був `U`, у `calculate.o` він став `T`, і linker їх зв'язав. `printf` linker дістав із libc.

```
main.o ─────────┐
                ├──→ Linker ──→ app
calculate.o ────┤
libc ───────────┘
```

## 8. ELF sections

```

```

Фрагмент для потрібних секцій (адреси, зсув у файлі, розмір):

| Section | Адреса | Offset | Розмір | Flags |
|---|---|---|---|---|
| `.text` | 0x1060 | 0x1060 | 0x142 | AX (код, виконується) |
| `.rodata` | 0x2000 | 0x2000 | 0x10 | A (лише читання) |

| `.bss` | 0x4014 | 0x3014 | 0xc | WA, тип **NOBITS** |

Прив'язка до нашої програми (`nm program` і `objdump`):

| Section | Що містить саме тут |

|---|---|---|---|

## 10. Розмір областей та велика `.bss`

```
size sections
```

Спочатку:

```
   text    data     bss     dec     hex  filename
   1450     608      16    2074     81a  sections
```
Розмір файлу: 16144 байти.

Після заміни `int uninitialized;` на `int large_array[100000];`:

```
   text    data     bss     dec     hex  filename
   1450     608  400040  402098   622b2  sections
```
Розмір файлу: 16160 байтів.

| | було | стало | різниця |
|---|---:|---:|---:|
| text | 1450 | 1450 | 0 |
| data | 608 | 608 | 0 |
| **bss** | 16 | **400040** | **+400 024** |
| розмір файлу, байт | 16144 | 16160 | **+16** |

**Чому `int large_array[100000]` збільшує `bss`, але не файл на ~400 000 байтів?**
Масив — глобальний і без початкового значення, тому він лежить у `.bss`, а `.bss` — це секція `NOBITS`. У файлі записано лише її розмір («потрібно 400040 байтів»), а не самі нулі. Реальну пам'ять під неї виділяє loader, коли програма запускається, і заповнює її нулями. Файл виріс лише на кілька службових байтів у заголовках секцій. Якби масив був ініціалізований (`= {1, 2, ...}`), його довелось би зберігати у `.data`, і файл справді виріс би приблизно на 400 000 байтів.

## 11. Dynamic libraries

```
$ ldd program
    linux-vdso.so.1 (0x00007f7f08671000)
    libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6 (0x00007f7f08400000)
    /lib64/ld-linux-x86-64.so.2 (0x00007f7f08673000)
```

Є `libc.so.6` — стандартна бібліотека C, в якій і реалізовано `printf`, а також `ld-linux-x86-64.so.2` — динамічний завантажувач (той самий `interpreter`, що ми бачили у `file`). `linux-vdso.so.1` — спеціальна «бібліотека», яку надає ядро.

**Чи є повна реалізація `printf()` у нашому executable?**
Ні. Розмір `program` — усього 16072 байти, а `main` викликає `printf` через заглушку `printf@plt` (див. `call 1050 <printf@plt>` вище); реальний `printf` лежить у `libc.so.6`.
**Що означає `.so`?** Shared object — спільна бібліотека.
**Чому кілька програм можуть використовувати одну?** Бібліотека завантажується в пам'ять один раз, а процеси підключають її код у свій адресний простір; код лише читається, тому ділитися ним безпечно.
**Яка перевага перед копіюванням в кожен executable?** Executable значно менші (у нас 16 КБ), оперативна пам'ять та диск економляться, а виправлення помилки в `libc` діє на всі програми без перекомпіляції.

| local | 0x7ffddc4023bc | stack | ✓ |

Прогноз підтвердився повністю.

**Які адреси близько одна до одної?**
Чотири глобальні/static змінні розташовані впритул: від `...2010` до `...2020`, різниця лише кілька байтів. Адреса `main` теж у тому ж образі програми (`0x55833285f...`), але в іншій секції: `.text` на 0x2e67 нижче.
**Чи `global_initialized` і `global_uninitialized` поруч?** Так, `...010` і `...01c`, різниця 12 байтів, хоча одна у `.data`, інша у `.bss`: ці секції стоять впритул одна до одної.
**Чи `local` поруч із глобальними?** Ні: `0x7ffddc4023bc` відрізняється від `0x558332862010` дуже сильно (старші цифри `7ff...` проти `558...`).
**Чи heap поруч із local?** Ні. Heap (`0x5583391df2a0`) починається з тих самих `0x558...`, що й образ програми, а stack — з `0x7ff...`. Між ними величезна відстань (десятки терабайт віртуального адресного простору).
**Що це говорить?** Адресний простір поділений на області: код і дані програми в одному місці, heap трохи вище, stack далеко вгорі.

## 14. Чи однакові адреси при кожному запуску?

Три запуски `./memory`:

| Об'єкт | Run 1 | Run 2 | Run 3 |
|---|---|---|---|
| main | 0x55833285f1a9 | 0x563292aa51a9 | 0x55b4732ee1a9 |
| global_initialized | 0x558332862010 | 0x563292aa8010 | 0x55b4732f1010 |
| local | 0x7ffddc4023bc | 0x7ffed3f6ea7c | 0x7ffe3b7c315c |
| dynamic | 0x5583391df2a0 | 0x5632c91302a0 | 0x55b477c882a0 |

**Чи однакові адреси?** Ні, вони щоразу інші. Це не помилка, а **ASLR** (Address Space Layout Randomization): ОС навмисно випадково зсуває початок образу програми, heap і stack, щоб ускладнити атаки, які покладаються на відомі адреси.

Спостереження: молодші 12 біт (три останні hex-цифри) не змінюються (`...1a9`, `...010`, `...2a0`), бо зсув кратний розміру сторінки (4096). Також не змінюється відстань між об'єктами одного образу: `global_initialized − main` у всіх трьох запусках дорівнює `0x2e67`. Тобто випадково зсувається образ програми цілком, а не кожна змінна окремо. Відстань до heap і stack щоразу інша.

## 15. Stack: `stack.c`

```
gcc -Wall -Wextra -O0 stack.c -o stack && ./stack
```

```
level1: &a = 0x7ffe9cd4c864
level2: &b = 0x7ffe9cd4c844
level3: &c = 0x7ffe9cd4c824
```

| Виклик | Адреса | Різниця від попередньої |
|---|---|---|
| level1 → `a` | ...c864 | |
| level2 → `b` | ...c844 | −0x20 (−32 байти) |
| level3 → `c` | ...c824 | −0x20 (−32 байти) |

**Чи змінюються адреси при вкладених викликах?** Так: кожен виклик створює новий stack frame, тому локальні змінні лежать на різних адресах.
**У якому напрямку?** Убік **зменшення**: чим глибший виклик, тим менша адреса.
**Чи узгоджується це з моделлю stack для x86-64?** Так, у цьому середовищі stack росте вниз (від вищих адрес до нижчих). Один frame тут займає 32 байти (збережений `rbp`, адреса повернення від `call`, локальна змінна та вирівнювання). Це спостереження стосується саме x86-64 Linux, не всіх архітектур.

## 16. Heap: `heap.c`

**Прогноз до запуску:** адреси `a`, `b`, `c` можуть виявитись близькими, але гарантії послідовності немає.

```
gcc -Wall -Wextra -O0 heap.c -o heap && ./heap
```

```
a: 0x55d03388c2a0
b: 0x55d03388c2c0
c: 0x55d03388c2e0
```

Адреси зростають із кроком `0x20` (32 байти), хоча `sizeof(int)` лише 4. Імовірно, allocator додає службовий заголовок і вирівнює блоки, тому кожен маленький блок займає мінімальну порцію.

У цьому запуску адреси виявились послідовними, але робити з цього правило «`malloc` завжди повертає послідовні адреси» не можна: allocator може повторно використовувати вільні блоки або брати пам'ять в іншому порядку. Головне, що експеримент показує: всі три адреси належать heap (`0x55d0...`), а не stack (`0x7ff...`).

## Відповіді на контрольні питання

1. **Етапи від C до executable:** preprocessing → compilation → assembling → linking, а потім loading під час запуску.
2. **Preprocessor:** обробляє директиви `#include`, `#define`, умовну компіляцію. Результат — `.i` (у нас 17 рядків стали 830).
3. **Compiler:** перетворює C-код (з `.i`) на Assembly (`.s`).
4. **Assembler:** перетворює Assembly на object file (`.o`) з machine code.
5. **Object file:** містить machine code, секції (`.text`, `.data`, `.bss`, `.rodata`), таблицю symbols та relocations.
6. **Навіщо linker:** об'єднує object files і бібліотеки, зіставляє імена (`U`) з визначеннями (`T`, `D`...) і підставляє справжні адреси замість нулів.
7. **Undefined reference:** linker не знайшов реалізації функції або змінної, яку хтось використовує (як `calculate`).
8. **Symbol:** ім'я функції чи змінної в object file, за яким linker їх знаходить (`nm` їх показує).
9. **Header і library:** header (`stdio.h`) містить лише оголошення, library (`libc`) — готову реалізацію. Header потрібен компілятору, library — linker.
10. **ELF:** стандартний формат виконуваних і object-файлів у Linux.
11. **`.text`:** машинні інструкції (у нас `add`, `main`, `_start`).
12. **`.rodata`:** константні дані лише для читання: рядок `"Result: %d\n"`, `message`.
13. **`.data` проти `.bss`:** `.data` — змінні з початковим значенням (їх значення зберігаються в файлі: `global_value = 10`, `initialized = 123`); `.bss` — змінні без значення (`global_empty`), які на старті нулюються.
14. **Чому велика `.bss` не збільшує файл:** бо `.bss` має тип NOBITS: у файлі записаний лише розмір, а нулі створює loader. У нас `bss` +400 024, а файл +16 байтів.
15. **`ldd`:** показує shared libraries, потрібні executable (у нас `libc.so.6` та `ld-linux-x86-64.so.2`).
16. **Executable проти process:** executable — файл на диску; process — його запущений екземпляр з PID, адресним простором і станом.
17. **Local variables:** у stack frame функції (`0x7ff...` у наших запусках).
18. **Heap:** для динамічної пам'яті, яку програма сама просить (`malloc`) та звільняє (`free`).
19. **Stack проти heap:** stack керується автоматично викликами функцій (у нас росте вниз, кожен frame 32 байти); heap керує програма, блоки живуть, доки їх не звільнять, і порядок адрес не гарантований.
20. **Чому адреси змінюються між запусками:** через ASLR, ОС випадково зсуває образ, heap і stack. Відстані всередині образу (наприклад, `0x2e67`) не змінюються.
21. **Temporal locality:** якщо до даних щойно зверталися, до них, імовірно, зверніться знову скоро (наприклад, змінна `sum` у циклі).
22. **Spatial locality:** якщо звернулись до адреси, імовірно, скоро звернуться й до сусідніх (елементи масиву підряд, змінні в одній секції). У нашому випадку близькі адреси `.data`/`.bss` це добре показують.

---

## Короткий висновок

Експериментально встановлено:

- `gcc program.c -o program` приховує чотири етапи: `.c` → `.i` (preprocessor, 17 → 830 рядків) → `.s` (compiler, текст Assembly) → `.o` (assembler, binary ELF) → executable (linker);
- в object file адреси `call` та посилань на змінні ще нульові, поруч є relocations; linker їх заповнює (`call 1149 <add>`), тому без реалізації `calculate` отримуємо `undefined reference`, а з `calculate.o` — працюючу програму;
- ELF64 PIE для x86-64 має секції `.text` (код), `.rodata` (константи), `.data` (змінні зі значенням) та `.bss` (змінні без значення); у `.bss` у файлі немає байтів, тому масив на 400 000 байтів збільшив `bss` на 400 024, а файл усього на 16 байтів;
- `printf` не копіюється в програму, а береться із `libc.so.6` під час запуску (`ldd`);
- executable — це файл, а process — його виконання з PID та власним адресним простором;
- у процесі адреси групуються за областями: `.text` → `.rodata` → `.data` → `.bss` → heap → stack, local-змінні у stack (`0x7ff...`), `malloc` у heap (`0x55...`);
- stack на x86-64 росте вниз (`−0x20` на кожен виклик), а `malloc` дає окремі блоки в heap без гарантій послідовності;
- адреси між запусками змінюються через ASLR, але відстані всередині образу програми сталі.

**Що з `/proc/PID` після завершення процесу?** Каталог зникає. Після завершення `process_info` команда `ls /proc/325` вивела `No such file or directory`.
**Чому `/proc` корисний для вивчення ОС?** Він робить внутрішній стан процесу видимим: ім'я, стан, PPID, пам'ять, виконуваний файл, без спеціальних інструментів.

## 4. System calls: `hello.c`

```
$ ./hello
Hello from process!
```

`strace ./hello` вивів 37 рядків. Фрагмент:

```

brk(NULL)                               = 0x556fa60af000
openat(AT_FDCWD, "/lib/x86_64-linux-gnu/libc.so.6", O_RDONLY|O_CLOEXEC) = 3
mmap(NULL, 2174352, PROT_READ, MAP_PRIVATE|MAP_DENYWRITE, 3, 0) = 0x7f0199a00000
```

Практично всі рядки — це запуск і підготовка (завантаження `libc`, виділення пам'яті), а наш вивід це лише один `write`.

З фільтром `strace -e write ./hello`:

```

```

(у реальному терміналі текст програми вклинюється всередину рядка strace, бо виводять обидва)

**Інтерпретація `write(1, "Hello from process!\n", 20) = 20`:**
- `1` — file descriptor stdout (стандартний вивід);
- `"Hello from process!\n"` — буфер, дані для запису;
- `20` — кількість байтів (19 символів + `\n`);
- результат `= 20` — скільки байтів ядро реально записало.

Шлях виведення: `printf()` → C library → `write` (system call) → ядро → stdout.

## 5. Library function проти system call: `output.c`

Запуск `strace -e write ./output` залежить від того, куди йде stdout.

**Якщо stdout перенаправлено у файл або pipe** (`./output > o.txt`, `./output | cat`):

```
write(1, "Output using write\n", 19)    = 19
write(1, "Output using printf\n", 20)   = 20
```

**Якщо stdout — термінал** (перевірив через псевдотермінал):

```
write(1, "Output using printf\n", 20)   = 20
write(1, "Output using write\n", 19)    = 19
```

Бачимо два `write`, але **в різному порядку**. Причина — buffering: `printf` не викликає `write` одразу. Якщо stdout — термінал, бібліотека буферизує по рядках і скидає буфер на `\n`, тому `printf` виходить першим. Якщо stdout — файл чи pipe, вона накопичує текст у буфері й скидає його лише при завершенні програми, тож прямий `write` встигає вийти раніше.

**Різниця між `printf` і `write`.** `printf` — функція бібліотеки C: форматує текст, буферизує його і лише потім (можливо, пізніше) звертається до ядра. `write` — прямий system call: дані одразу йдуть у ядро. Тому не можна стверджувати, що кожен `printf` дорівнює одному `write`.

## 6. Перший `fork()`: `fork_basic.c`

```
$ ./fork_basic
Before fork: PID=386
PARENT: PID=386, child PID=387, fork returned=387
CHILD:  PID=387, PPID=386, fork returned=0
```

```
Parent PID = 386
Child PID  = 387
Child PPID = 386
```

**Скільки процесів було до `fork()`?** Один.
**Скільки після успішного `fork()`?** Два: parent і child.
**Що отримав parent?** PID дитини (387).
**Що отримав child?** `0`.
**Чому один рядок `pid_t pid = fork();` веде двома шляхами?** `fork()` створює майже точну копію процесу, і обидва процеси продовжують виконання з місця одразу після виклику. Різниця тільки в поверненому значенні: у батька `pid > 0`, у дитини `pid == 0`. Далі `if (pid == 0)` розводить їх по різних гілках.

```
             Process (386)
                │
              fork()
                │
          ┌─────┴─────┐
          ▼           ▼
   Parent (386)   Child (387)
   pid = 387      pid = 0
```

### Порядок виконання

Запустив `./fork_basic` 20 разів і подивився, що друкується першим після `Before fork`:

| Перший надрукував | Разів з 20 |
|---|---:|
| PARENT | 14 |
| CHILD | 6 |

**Чи можна гарантувати порядок?** Ні. Після `fork()` це два незалежні процеси, і який із них отримає процесор першим, вирішує планувальник ОС (scheduler). Це перший приклад concurrency: результат залежить не від коду, а від планування.

## 8. `fork()` через `strace`: `strace -f -e trace=process ./fork_basic`

```
execve("./fork_basic", ["./fork_basic"], ...) = 0
Before fork: PID=492
clone(child_stack=NULL, flags=CLONE_CHILD_CLEARTID|CLONE_CHILD_SETTID|SIGCHLD, ...) = 493
strace: Process 493 attached
PARENT: PID=492, child PID=493, fork returned=493
[pid   492] exit_group(0)               = ?
CHILD:  PID=493, PPID=492, fork returned=0
[pid   492] +++ exited with 0 +++
exit_group(0)                           = ?
+++ exited with 0 +++
```

- створення child: `clone(...) = 493`, а PID дитини — 493;
- `strace: Process 493 attached` — strace почав стежити за новим процесом (опція `-f`);
- завершення: `exit_group(0)` у батька і в дитини.

**Важливе спостереження.** У C ми викликали `fork()`, а в trace немає жодного рядка `fork(`. Є `clone(...)`. `fork()` — це функція бібліотеки (API), а ядро отримує конкретний системний виклик `clone` з набором прапорців. Назви API і системного виклику не обов'язково збігаються.

## 9. `wait()` і exit status: `wait_basic.c`

```
$ time ./wait_basic
CHILD: working...
CHILD: finished
PARENT: waiting for child 495
PARENT: child finished
PARENT: child exit status = 42

real    0m2.002s
```

Тут вивід ішов не в термінал, тому текст батька (без `fflush`) скидався з буфера лише при завершенні й «спізнився» за рядками дитини. Це та сама буферизація, що в `output.c`. Порядок можна було б побачити іншим, але логіка не змінюється: `child finished` не з'являється раніше за завершення дитини, і програма працює ~2 с.

Із `strace -f -e trace=process`:

```
clone(...) = 502
[pid   501] wait4(-1,  <unfinished ...>
[pid   502] exit_group(42)              = ?
[pid   502] +++ exited with 42 +++
<... wait4 resumed>[{WIFEXITED(s) && WEXITSTATUS(s) == 42}], 0, NULL) = 502
--- SIGCHLD {si_signo=SIGCHLD, si_code=CLD_EXITED, si_pid=502, ..., si_status=42, ...} ---
```

**Що робить parent під час `wait()`?** Блокується: його стан змінюється на «очікування» (`wait4` не повернувся), він не споживає процесор, доки child не завершиться. Програма працює рівно ~2 секунди, поки спить child.
**Чому «PARENT: child finished» не з'являється раніше?** Бо `wait()` повертає керування лише після завершення дитини. У `strace` видно, що `wait4` «resumed» тільки після `exit_group(42)`.
**Що означає 42?** Exit status: число, яке child повернув із `main` (`return 42`).
**Чи 42 є PID?** Ні. PID дитини — 502, а 42 — код завершення, який дитина обрала сама.
**Навіщо `WIFEXITED` та `WEXITSTATUS`?** `status` у `wait` — закодоване число, в якому зібрано різну інформацію (нормальне завершення чи вбито сигналом, код виходу). `WIFEXITED(status)` перевіряє, що child завершився нормально, а `WEXITSTATUS(status)` витягує з нього код виходу (42).

## 13. Стани процесу: `states.c`

```
$ ./states
PID=527
```

```
$ grep -E '^(Name|State):' /proc/527/status
Name:   states
State:  S (sleeping)

$ ps -o pid,ppid,state,cmd -p 527
  PID  PPID S CMD
  527   526 S ./states

$ awk '{print "utime="$14, "stime="$15}' /proc/527/stat
utime=0 stime=0
```

**Під час `sleep()` процес:** не використовує CPU (utime та stime = 0 тактів), не *running*, а **waiting/sleeping** (стан `S`).

**Чому ОС не повинна витрачати CPU на процес, що чекає таймера?** Він нічого не обчислює: йому просто нема що виконувати. Ядро прибирає його з черги готових до виконання і повертає туди, коли спрацює таймер. Весь цей час процесор вільний для інших процесів. Якби ОС давала йому час, вона б марно витрачала ресурс.

Моделі станів: *Ready* — готовий і чекає процесор, *Running* — зараз виконується на процесорі, *Waiting* — чекає події (таймер, ввід/вивід).

## 14. Zombie: `zombie.c`

Child одразу завершується, а parent 60 секунд спить і `wait()` не викликає.

```
$ ./zombie
PARENT: PID=552, child=553
PARENT: sleeping without wait()
CHILD: PID=553, exiting now
```

Стан дитини:

```
$ ps -o pid,ppid,state,cmd -p 553
  PID  PPID S CMD
  553   552 Z [zombie] <defunct>

$ grep -E '^(Name|State|PPid):' /proc/553/status
Name:   zombie
State:  Z (zombie)
PPid:   552
```

`/proc/553/cmdline` порожній (0 байтів), а `readlink /proc/553/exe` нічого не виводить: програми в процесі вже немає. Батько при цьому живий (`S`).

**Виправлення:** `zombie_fixed.c` викликає `wait(NULL)` (спочатку спить 10 с, щоб було видно zombie):

```
-- до wait() (t≈1.5 с):
  572   571 Z [zombie_fixed] <defunct>

-- після wait() (t≈11.5 с):
PARENT: wait() done, child collected
  PID  PPID S CMD                  ← порожньо, запису про child немає
```

```
Child
 │ exit
 ▼
Terminated ── статус не забрано ──► Zombie
                                       │ parent: wait()
                                       ▼
                                    Removed
```

**Що таке zombie?** Процес, який уже завершився, але в таблиці процесів лишається його запис (PID і exit status), доки parent не викличе `wait()` і не забере цей статус.
**Чи виконує він інструкції?** Ні. Код не виконується і CPU він не споживає, бо програми вже немає. Залишається лише службовий запис, який займає PID.

Якщо parent помирає раніше, child стає «сиротою»: його PPID змінюється на 1 (так було й у моєму експерименті після `kill` батька).

|---|---:|
| 1 | 2 |

| 3 | 8 |

### Process tree

`fork_tree.c` те саме, але з `sleep`, щоб батьки були живі, коли діти питають `getppid()` (без цього частина процесів друкує `PPID=1`: їхні батьки вже завершились, і їх «усиновив» процес 1):

## 16. Фінальна програма: `process_runner.c`

Програма: показує PID батька → `fork()` → у child друкує PID і PPID та через `execvp` запускає передану програму (з аргументами, якщо вони є) → у parent `waitpid()` → розбирає, як завершився child (нормально, сигналом чи інакше) → продовжує. Помилки `fork`, `exec` і `waitpid` перевіряються. Якщо `exec` не вдався, child завершується зі статусом `127` (так само роблять shell).

```
$ ./process_runner date
Parent PID: 627
Creating child...

Child PID: 628
Child PPID: 627
Executing: date

Wed Oct 14 ...

Child 628 completed
Exit status: 0

Parent continues
```

Інші випадки:

```
$ ./process_runner echo hi there      → Executing: echo / hi there / Exit status: 0
$ ./process_runner false              → Exit status: 1
$ ./process_runner no_such_program
exec no_such_program: No such file or directory
Child 638 completed
Exit status: 127
$ ./process_runner sh -c 'kill -9 $$'
Child 641 completed
Killed by signal: 9 (Killed)
$ ./process_runner                    → Usage: ./process_runner PROGRAM [args...]
```

### `strace -f -e trace=process ./process_runner date`

Три потрібні фрагменти (рядки про пошук у `PATH` скорочено):

**Створення процесу:**
```
clone(child_stack=NULL, flags=CLONE_CHILD_CLEARTID|CLONE_CHILD_SETTID|SIGCHLD, ...) = 650
```

**Запуск нового program image:**
```
[pid   650] execve("/usr/bin/date", ["date"], ...) = 0
```

**Очікування і завершення child:**
```
wait4(650,  <unfinished ...>
[pid   650] exit_group(0)               = ?
<... wait4 resumed>[{WIFEXITED(s) && WEXITSTATUS(s) == 0}], 0, NULL) = 650
--- SIGCHLD {si_signo=SIGCHLD, si_code=CLD_EXITED, si_pid=650, si_status=0, ...} ---
```

Зіставлення з кодом:

| Код C | Системний виклик ядра |
|---|---|
| `fork()` | `clone(...) = 650` |
| `execvp("date", ...)` | `execve("/usr/bin/date", ...)` |
| `waitpid(pid, &status, 0)` | `wait4(650, ...)` |
| `return` / `_exit` | `exit_group(0)` |
| `WIFEXITED`, `WEXITSTATUS` | розбір статусу `WIFEXITED(s) && WEXITSTATUS(s) == 0` |

Є і додатковий результат: коли child завершується, батькові приходить сигнал `SIGCHLD`. Так ядро повідомляє про завершення дитини.

## Відповіді на контрольні питання

1. **Program і process.** Program — файл на диску з кодом і даними. Process — запущений екземпляр програми з PID, пам'яттю та станом.
2. **PID.** Числовий ідентифікатор процесу, який видає ядро.
3. **PPID.** PID батьківського процесу, який створив поточний.
4. **Чому один executable має декілька PID?** Кожен запуск створює окремий процес (у нас три запуски `process_info` дали PID 295, 296, 297).
5. **Роль `/proc/PID`.** Віртуальний каталог ядра, через який видно стан процесу: ім'я, стан, PPID, `exe`, `maps`, `cmdline`.
6. **System call.** Запит програми до ядра ОС на виконання привілейованої дії (запис, створення процесу, запуск програми).
7. **Function call проти system call.** Звичайна функція виконується в просторі програми. System call передає керування ядру. Бібліотечна функція (`printf`) може викликати `write` усередині, але не обов'язково щоразу.
8. **Роль `strace`.** Показує, які системні виклики робить програма, з аргументами та результатами.
9. **`fork()`.** Створює дочірній процес, майже точну копію поточного.
10. **Скільки процесів після одного `fork()`?** Два.
11. **Чому `fork()` повертає 0 у child?** Щоб процеси могли розрізнити себе: дитині 0, а батькові PID дитини (щоб потім на неї чекати). Свій PID дитина дізнається через `getpid()`, а PID батька через `getppid()`.
12. **Що отримує parent?** PID дитини (387 у нашому запуску).
13. **Чи спільна `value`?** Ні. Після `fork()` у кожного своя копія (батько 300, дитина 200).
14. **Чому однакові virtual addresses не означають спільну пам'ять?** Адреси віртуальні й діють у межах свого адресного простору. Однакове число в двох процесах відображається на різну фізичну пам'ять (`0x56110f84c010` у батька й дитини, але значення 300 і 200).
15. **`exec()`.** Замінює програму поточного процесу новою: код, дані, стек.
16. **Чи створює `exec()` новий процес?** Ні.
17. **PID після успішного `exec()`.** Не змінюється (506 до і після).
18. **Навіщо `wait()`.** Щоб parent дочекався завершення child, синхронізувався з ним і забрав exit status. Без цього залишається zombie.
19. **Exit status.** Код, з яким процес завершився (`return 42`). Нуль зазвичай означає успіх.
20. **Zombie.** Завершений процес, чий exit status ще не зібраний батьком (`Z`, `<defunct>`).
21. **Чи виконує zombie інструкції?** Ні, не виконує й не споживає CPU. Залишається лише запис про завершення.
22. **Ready, Running, Waiting.** Ready: процес готовий і чекає процесор. Running: виконується на процесорі зараз. Waiting: чекає події (таймер, ввід/вивід), процесор не потрібен (`State: S`).
23. **Чому порядок parent/child не гарантований?** Після `fork()` це два незалежні процеси, і планувальник сам вирішує, якому дати процесор першим (у 20 запусках парент був першим 14 разів, а дитина 6).
24. **Як `fork → exec → wait` пов'язаний із shell?** Shell так запускає кожну команду: `fork()` створює дитину, у ній `exec()` запускає програму (`date`, `ls`), а shell робить `wait()` і лише потім показує наступне запрошення. Наші `launcher` та `process_runner` реалізують саме це.

## Короткий висновок

Експериментально встановлено:

- програма це файл, а процес його запущений екземпляр: один `process_info` дав три різні PID, а `/proc/PID` показує стан живого процесу й зникає після його завершення;


## 5. Race condition: `race.c`

Два threads, кожен по 1 000 000 разів робить `counter++` без захисту. Очікується `2000000`.

П'ять перших запусків:

| Run | Expected | Actual |
|---:|---:|---:|
| 1 | 2000000 | 2000000 |
| 2 | 2000000 | 2000000 |
| 3 | 2000000 | 2000000 |
| 4 | 2000000 | **1114953** |
| 5 | 2000000 | 2000000 |

Тут помилка трапилась лише один раз із п'яти. Тому я перевірив докладніше:

| Умови | Запусків | Неправильний результат | Мінімум | Медіана | Максимум |
|---|---:|---:|---:|---:|---:|
| 2 threads × 1 000 000 | 100 | **10** | 1 000 000 | 2 000 000 | 2 000 000 |
| 2 threads × 10 000 000 (`-DITERATIONS=10000000`) | 20 | **20** | 11 090 365 | 14 123 562 | 19 944 325 |

П'ять запусків при 10 000 000 ітерацій (очікувалося 20 000 000): `15207094`, `15872485`, `15309868`, `13231287`, `11360278`.

Спостереження:
- на малій кількості ітерацій thread 1 може майже закінчити роботу до того, як стартує thread 2 (старт threads займає час), тому перетин по часу невеликий і помилка трапляється рідко;
- при більшій кількості ітерацій threads гарантовано працюють одночасно, і неправильним є **кожен** запуск;
- результати щоразу різні: це залежить від timing і interleaving;
- найгірший випадок `1000000` означає, що майже всі інкременти одного thread були втрачені;
- **успішні запуски нічого не доводять**: програма некоректна, навіть якщо кілька разів вийшло `2000000`.

(З `-O2` на 1 000 000 всі 20 запусків дали `2000000`: компілятор замінив весь цикл на одну інструкцію, див. розділ 7. Це не робить програму коректною.)

## 6. Lost update

У C один рядок `counter++`, а концептуально це три кроки:

```
READ counter → ADD 1 → WRITE counter
```

Нехай `counter = 100`. Можливий interleaving:

```
Thread A                 Thread B

READ 100
                         READ 100
ADD → 101
                         ADD → 101
WRITE 101
                         WRITE 101
```

Очікували `102`, отримали `101`: інкремент Thread A **втрачено**, бо Thread B прочитав старе значення, до того як A записав нове. Це lost update.

## 7. Машинні інструкції для `counter++`

```
gcc -Wall -Wextra -pthread -O0 -S -masm=intel race.c -o race.s
objdump -d -M intel race
```

Фрагмент `<increment>` (`-O0`):

```
11bf:  48 8b 05 52 2e 00 00   mov    rax,QWORD PTR [rip+0x2e52]   # 4018 <counter>   ← READ
11c6:  48 83 c0 01            add    rax,0x1                                           ← ADD 1
11ca:  48 89 05 47 2e 00 00   mov    QWORD PTR [rip+0x2e47],rax   # 4018 <counter>   ← WRITE
11d1:  48 83 45 f8 01         add    QWORD PTR [rbp-0x8],0x1       ← i++
11d6:  48 81 7d f8 3f 42 0f 00 cmp   QWORD PTR [rbp-0x8],0xf423f   ← i <= 999999
11de:  7e df                  jle    11bf <increment+0x16>
```

**Чи виглядає `counter++` як одна неподільна операція?** Ні. Це три окремі інструкції: `mov` (читання з пам'яті в регістр), `add` (збільшення у регістрі), `mov` (запис назад). Між ними будь-який інший thread може прочитати або записати `counter`, і саме це дає lost update.

Одна C-операція це не одна інструкція процесора, а процесор може перемкнутись між threads між будь-якими двома інструкціями (зв'язок із Lab 2).

З `-O2` (для порівняння) весь цикл звівся до однієї інструкції:

```
increment:
    endbr64
    add     QWORD PTR counter[rip], 1000000
    xor     eax, eax
    ret
```

Це пояснює, чому з `-O2` гонка не проявилась: вікно для втрати майже зникло. Але інструкція все одно не має префікса `lock`, тобто не гарантовано атомарна: коректність тримається на везінні, а не на гарантії.

## 8. Що саме в програмі є race condition

```
Thread 1 ───┐
            ▼
          counter
            ▲
Thread 2 ───┘
```

```
Shared state:       змінна counter (глобальна long)
Concurrent writers: thread1 та thread2 (обидва виконують increment)

```

Race condition: результат залежить від того, як перемежовуються (interleave) операції threads, а це визначається timing і scheduler.

## 9. Critical section і mutex

Критична операція це `counter++`. Потрібно, щоб поки один thread її виконує, другий чекав:

```
Thread A         Thread B
LOCK             LOCK  ← чекає, поки A не віддасть
counter++
UNLOCK
                 counter++
                 UNLOCK
```

Для цього використовується mutex (mutual exclusion): `pthread_mutex_lock()` перед критичною секцією і `pthread_mutex_unlock()` після.

## 10. Виправлення: `mutex_counter.c`

Результати п'яти запусків і порівняння з `race.c` (ті самі п'ять запусків із розділу 5):

| Run | `race.c` | `mutex_counter.c` |
|---:|---:|---:|
| 1 | 2000000 | 2000000 |
| 2 | 2000000 | 2000000 |
| 3 | 2000000 | 2000000 |
| 4 | **1114953** | 2000000 |
| 5 | 2000000 | 2000000 |

Для `race.c` це лише пощастило в 4 запусках, а `mutex_counter.c` дає правильний результат завжди (перевірив і при 10 000 000 ітерацій у розділі 12).

**Чому mutex змінив поведінку?** `pthread_mutex_lock()` пускає в критичну секцію лише один thread. Якщо mutex вже належить іншому, thread блокується й чекає, поки власник викличе `pthread_mutex_unlock()`. Тому READ, MODIFY, WRITE одного thread не перемежовуються з такими самими кроками іншого, і втрати оновлень немає. Це mutual exclusion: у critical section одночасно не більше одного thread.

```
            Mutex
              │
      ┌───────┴───────┐
 Thread A         Thread B
```

## 11. Де має бути lock: `mutex_wide.c`

Два варіанти:

```c
/* вузький: lock на кожну ітерацію (mutex_counter.c) */
for (...) { lock; counter++; unlock; }

/* широкий: lock на весь цикл (mutex_wide.c) */
lock; for (...) { counter++; } unlock;
```

Обидва правильні (`mutex_wide` теж дав `2000000` в усіх запусках). Різниця в тому, як працюють threads:

```
Thread A  ── holds mutex ──[ 1 000 000 increments ]──
Thread B  ── WAIT ───────────────────────────────────  потім свої 1 000 000
```

У широкому варіанті Thread B нічого не робить, доки A не закінчить, тобто паралелізму немає: threads працюють по черзі. У вузькому варіанті threads чергуються на кожному кроці. Висновок: critical section має бути достатньою для correctness, але без потреби не надто великою.

(У цій програмі, де вся робота і є critical section, широкий lock вийшов навіть швидшим, див. розділ 12: немає боротьби за mutex на кожному кроці. Але в реальній програмі, де в threads є ще й некритична робота, широкий lock зведе паралелізм нанівець.)

| `race` (1M) | 0,009 с | 0,009 с | 0,009 с |
| `mutex_counter` (1M) | 0,124 с | 0,096 с | 0,131 с |
| `mutex_wide` (1M) | 0,007 с | 0,007 с | 0,012 с |
| `race` (10M) | 0,057 с | 0,049 с | 0,050 с |
| `mutex_counter` (10M) | 1,105 с | 1,374 с | 1,208 с |
| `mutex_wide` (10M) | 0,045 с | 0,046 с | 0,047 с |

`mutex_counter` у 10–25 разів повільніший за `race`. Це не точний benchmark, а демонстрація концепції. У `time` видно, куди йде час: при 10M ітерацій у `mutex_counter` `sys` ≈ 0,4–0,6 с (звернення до ядра через futex), а в `race` майже 0.

**Чому synchronized програма може бути повільнішою?**
- кожне `lock`/`unlock` це додаткові операції, а коли mutex зайнятий, thread засинає й ядро його будить (системні виклики);
- lock contention: threads змагаються за один mutex, і замість роботи чекають;
- в кожній ітерації мільйон разів платимо за синхронізацію заради однієї інструкції.

```
Synchronization → correctness + overhead / contention
```

## 13. Більше threads: `race_four.c`, `mutex_four.c`

4 threads × 500 000 increments, очікується `2000000`.

`race_four` (без mutex), п'ять запусків: `1677442`, `2000000`, `1162875`, `1084634`, `1258489`.
`mutex_four` (з mutex), п'ять запусків: `2000000` у всіх.

| Варіант | Неправильних результатів | Типовий час |
|---|---|---:|
| 2 threads без mutex | 10 зі 100 | 0,009 с |
| 4 threads без mutex | **87 зі 100** (мінімум 273 015) | 0,008 с |
| 2 threads з mutex | 0 з 5 | 0,096–0,131 с |
| 4 threads з mutex | 0 з 5 | 0,099–0,135 с |

**Чи означає більше threads автоматично швидшу програму?** Ні. Тут:
- без mutex чотири threads лише збільшили кількість помилок: майже кожен запуск неправильний;
- з mutex чотири threads не швидші за два (0,10–0,13 с проти 0,10–0,13 с), бо працювати може лише один thread за раз, а решта чекають; до того ж у машині лише 2 ядра;
- швидше стає тільки тоді, коли threads справді працюють одночасно над незалежними частинами, як у `parallel_sum`.

## 14. Shared heap: `shared_heap.c`

```
$ ./shared_heap
Worker: value=110 address=0x55bb4fe372a0
Main: value=110 address=0x55bb4fe372a0
```

**Де знаходиться `data`?** У heap (виділена через `malloc`; адреса `0x55bb...` разом з образом програми, а не `0x7ff...`, як stack).
**Чи бачить worker ту саму пам'ять?** Так: однакова адреса, і Main прочитав `110`, тобто зміну, зроблену worker.
**Чому?** Heap один на весь процес, а ми передали thread вказівник. Thread має власний stack, але heap спільний.
**Що змінилося б, якби кілька threads одночасно робили `data->value += 10`?** Вийшла б така сама race condition, як із `counter++`: `+=` це теж READ-MODIFY-WRITE, тому частина збільшень втрачалась би (потрібен mutex).

## 15. Повернення результату: `thread_result.c`

```
$ ./thread_result
Result = 144
```

**Чому не можна `int result = value * value; return &result;`?** `result` це локальна змінна, і вона лежить на stack thread-а. Коли функція повертається (thread завершується), цей stack перестає існувати. Вказівник `&result` вказує на пам'ять, якої вже немає (dangling pointer), і читати її це undefined behavior. Тому результат створюється в heap через `malloc`: heap живе, доки його не звільнять, і main після `pthread_join` отримує коректний вказівник (і сам робить `free`).

```
result → local variable → stack thread-а → зникає, коли функція завершилась
```

## 16. Deadlock: спочатку аналіз

```
Thread A:  lock(mutex1)  →  lock(mutex2)
Thread B:  lock(mutex2)  →  lock(mutex1)
```

Можливе виконання:

```
Thread A                  Thread B

lock mutex1               lock mutex2     ← кожен узяв по одному

lock mutex2 ✗ чекає       lock mutex1 ✗ чекає
(належить B)              (належить A)

       ↓                      ↓
             DEADLOCK
```

Обидва можуть зупинитись назавжди: A тримає mutex1 і чекає на mutex2, а B тримає mutex2 і чекає на mutex1. Жоден не може продовжити, бо чекає на те, що утримує інший, і жоден не віддасть свій mutex, поки не отримає другий.

## 17. Спостереження: `deadlock.c`

```
$ ./deadlock
Thread 1: locking mutex1
Thread 2: locking mutex2
Thread 1: locking mutex2
Thread 2: locking mutex1
                              ← далі нічого, програма зависла
```

Тут не з'являється «critical section» ні в одного thread. Три запуски під `timeout 4` усі завершились кодом `124`, тобто програма не завершилась сама.

Стан завислого процесу (`ps -L`):

```
  PID   TID S WCHAN                CMD
 1940  1940 S futex_do_wait        ./deadlock      ← main (чекає pthread_join)
 1940  1942 S futex_do_wait        ./deadlock      ← Thread 1
 1940  1943 S futex_do_wait        ./deadlock      ← Thread 2
```

Усі три threads у стані `S` і чекають на futex; `/proc/PID/status` показує `Threads: 3`; `utime=0 stime=0`, тобто CPU не споживається. Через 6 секунд процес досі живий. (Це також ще один спосіб побачити: у процесі один PID, а threads мають різні TID.)

Є деталь: якщо перенаправити вивід у файл (`./deadlock > out.txt`), у файлі буде порожньо (0 байтів), бо `stdout` буферизується, а програма ніколи не завершується й не скидає буфер. Щоб побачити рядки, я запускав через `stdbuf -oL`.

```
Thread 1 → хоче mutex2 → належить Thread 2
   ▲                              │
   │                              ▼
   └──── mutex1 ◄── хоче ── Thread 2
```

Це **circular wait**: Thread 1 → mutex2 → Thread 2 → mutex1 → Thread 1.

## 18. Виправлення: `deadlock_fixed.c`

У `worker2` замінив порядок на `mutex1`, потім `mutex2` (як у `worker1`):

```
$ ./deadlock_fixed
Thread 2: locking mutex1
Thread 1: locking mutex1
Thread 2: locking mutex2
Thread 2: critical section
Thread 1: locking mutex2
Thread 1: critical section

real    0m2.003s
```

Програма завершилась (код 0) в усіх п'яти запусках. Час 2 секунди: Thread 2 тримає mutex1 і спить `sleep(1)`, потім Thread 1 чекає й бере його ще на секунду.

**Яку умову deadlock усунули?** Circular wait (циклічне очікування). Коли всі threads беруть mutex у одному порядку (спершу mutex1, потім mutex2), цикл «A чекає B, B чекає A» неможливий: той, хто взяв mutex1 першим, завжди зможе взяти й mutex2, бо другий thread зупиниться ще на mutex1.

## 19. Race condition ≠ deadlock

| Характеристика | Race Condition | Deadlock |
|---|---|---|
| Threads продовжують execution? | Так, виконуються далі | Ні, заблоковані назавжди |
| Результат може бути неправильним? | Так (1114953 замість 2000000) | Результату взагалі немає, програма зависає |
| Програма може повністю перестати прогресувати? | Ні | Так |
| Пов'язано з timing/order? | Так (interleaving) | Так (залежить від порядку взяття lock) |
| Mutex може допомогти? | Так, це основний засіб | Ні: mutex якраз і причина |
| Неправильне використання mutex може бути причиною? | Так: відсутній або неповний захист | Так: неправильний порядок блокувань |

```
No synchronization        →  Race Condition
Incorrect synchronization →  Deadlock
```

Synchronization потрібна, але її теж треба проєктувати правильно.

## 20. Фінальне завдання: `parallel_sum.c`

Сума 1 + 2 + … + N на 4 threads; кожен рахує свій діапазон у локальній змінній `sum` і записує результат у власну структуру `Task`.

```
$ ./parallel_sum
Thread 1: 1 ... 250000 = 31250125000
Thread 2: 250001 ... 500000 = 93750125000
Thread 3: 500001 ... 750000 = 156250125000
Thread 4: 750001 ... 1000000 = 218750125000

Parallel result: 500000500000
Expected result: 500000500000

Correct: YES
```

Перевірка за формулою `N × (N + 1) / 2 = 1000000 × 1000001 / 2 = 500000500000` збігається. Програма також правильно працює, якщо N не ділиться на 4 (`./parallel_sum 1000003` дало `500003500006`, `Correct: YES`; останній thread бере залишок), а також з `N = 1 000 000 000` (`500000000500000000`).

### Аналіз

**1. Які data shared?** Масив `tasks` (доступний main і worker threads через вказівник), а також усі глобальні дані та heap процесу.
**2. Які data thread-local?** Змінна `sum` усередині `calculate_sum()` і лічильник циклу `i`: вони на stack кожного thread.
**3. Чому threads не потребують mutex у циклі?** Кожен thread змінює лише власний local accumulator і власний `Task`. Ніхто більше їх не чіпає, тому немає ні shared mutable state, ні гонки.
**4. Коли main читає результати?** Лише після `pthread_join()` для відповідного thread. Join гарантує, що thread закінчив запис `task->result`.
**5. Чому цей design кращий за один глобальний counter з lock на кожній ітерації?** Синхронізація потрібна один раз на thread (при збиранні результатів), а не 250 000 разів. З розділу 12 видно, що lock на кожному кроці може коштувати в десятки разів повільніше. Найкращий спосіб розв'язати race condition інколи не додавати більше locks, а зменшити shared mutable state.

### Додатково: sequential проти 4 threads

`sequential_sum.c` рахує те саме в одному thread.

| N | `sequential_sum` (real) | `parallel_sum` (real) |
|---|---|---|
| 1 000 000 | 0,005 с (×3) | 0,004 с (×3) |
| 1 000 000 000 | 2,653 / 2,658 / 2,705 с | 1,134 / 1,126 / 1,195 с |

Для 1 000 000 різниця непомітна: самої роботи так мало, що вона співмірна з вартістю створення threads. Для великого N 4 threads дали виграш ≈ 2,3 рази, а не 4: у машині лише 2 ядра (вище за 2 не стрибнеш; частина виграшу в тому, що цикл у `parallel_sum` при `-O0` трохи дешевший за цикл у `sequential_sum`, видно з `user` часу).

**За яких умов parallelization має сенс?**
- задача достатньо велика, щоб вартість створення threads була малою порівняно з роботою;
- її можна розділити на незалежні частини, які майже не потребують спільних даних і блокувань;
- є достатньо ядер (4 threads на 2 ядрах не дадуть 4× швидкості);
- результати збираються рідко (раз наприкінці), а не на кожному кроці.

## Відповіді на контрольні питання

1. **Що таке thread?** Одиниця виконання всередині процесу зі своїм стеком і регістрами. Процес може мати кілька threads.
2. **Чим thread відрізняється від process?** Процеси мають окремі адресні простори (як після `fork`), а threads одного процесу діляться одним адресним простором. Створити thread дешевше, але вони легше заважають одне одному.
3. **Що threads одного процесу поділяють?** Код, глобальні й static дані (`.data`, `.bss`), heap, відкриті файли.
4. **Що кожен thread має власне?** Stack, регістри (включно з лічильником інструкцій), власний ідентифікатор (TID).
5. **Чи має кожен thread власний stack?** Так (`local` у `thread_stacks` мають різні адреси, на 8 МБ + 4 КБ одна від одної).
6. **Чи мають threads спільний heap?** Так, `shared_heap` показав однакову адресу та зміну значення.
7. **Для чого `pthread_create()`?** Створює новий thread, який починає виконувати вказану функцію з переданим аргументом.
8. **Для чого `pthread_join()`?** Чекає завершення thread і (за потреби) забирає його результат.
9. **Чи гарантується порядок виконання threads порядком `pthread_create()`?** Ні, його визначає scheduler (у `multiple_threads` порядок щоразу різний).
10. **Concurrency проти parallelism?** Concurrency означає, що кілька задач просуваються в перемежованому порядку (можливо, на одному ядрі). Parallelism означає, що вони справді виконуються одночасно на різних ядрах.
11. **Shared state?** Дані, до яких мають доступ кілька threads (тут `counter`).
12. **Race condition?** Ситуація, коли результат залежить від порядку або timing виконання threads, що одночасно звертаються до shared state (хоча б один пише).
13. **Lost update?** Оновлення, перезаписане іншим thread-ом: обидва прочитали старе значення, і один запис «затер» інший (101 замість 102).
14. **Чому `counter++` не atomic?** Це три інструкції (`mov` читання, `add`, `mov` запис), і між ними може втрутитись інший thread.
15. **Critical section?** Ділянка коду, яка працює із shared state й не має виконуватись одночасно кількома threads (`counter++`).
16. **Mutual exclusion?** Гарантія, що в critical section у кожен момент не більше одного thread.
17. **Mutex?** Об'єкт-замок, який реалізує mutual exclusion: його може тримати лише один thread.
18. **Що робить `pthread_mutex_lock()`?** Захоплює mutex; якщо він вільний, thread одразу проходить далі.
19. **Що, якщо mutex уже належить іншому thread?** Thread блокується (засинає), доки власник не викличе unlock.
20. **Навіщо `pthread_mutex_unlock()`?** Віддає mutex, щоб інші threads могли зайти в critical section. Без unlock всі інші чекали б вічно.
21. **Чому надто велика critical section погіршує concurrency?** Бо поки один thread тримає mutex, решта чекають, і паралелізм зникає (`mutex_wide`: Thread B стоїть, доки A не зробить мільйон кроків).
22. **Lock contention?** Конкуренція threads за один і той самий lock: вони витрачають час на очікування (у `mutex_counter` це дало 10–25× повільнішу роботу).
23. **Чому більше threads не обов'язково означає більшу performance?** Ядер обмежена кількість, threads потрібно створювати, синхронізувати й чекати один на одного (4 threads з mutex не швидші за 2; без mutex у 4 threads 87% запусків неправильні).
24. **Deadlock?** Стан, коли threads чекають одне на одного нескінченно й жоден не може продовжити (`deadlock.c`).
25. **Чим deadlock відрізняється від race condition?** Race: програма працює, але результат може бути неправильний. Deadlock: програма зависає й результату немає; його спричиняє неправильне використання locks.
26. **Circular wait?** Цикл очікування: Thread 1 чекає ресурс Thread 2, а Thread 2 чекає ресурс Thread 1.
27. **Як однаковий порядок блокувань допомагає?** Усуває circular wait: коли всі беруть mutex у тому самому порядку, цикл неможливий (`deadlock_fixed`).
28. **Starvation?** Ситуація, коли thread дуже довго (можливо, нескінченно) не отримує потрібного ресурсу (наприклад, mutex), бо його постійно випереджають інші, хоч програма в цілому працює.
29. **Чому local accumulation краще за shared counter із mutex на кожній ітерації?** Синхронізація потрібна один раз, а не мільйон; threads не конкурують за lock і справді працюють паралельно.
30. **Чому 100 успішних запусків не доводять відсутність race condition?** Гонка залежить від timing: у `race.c` 90 запусків зі 100 дали правильний результат, але програма все одно некоректна. Відсутність помилки у тестах не доводить відсутність помилки в програмі.

## Короткий висновок

Експериментально встановлено:

- threads одного процесу діляться пам'яттю (код, дані, heap): адреса `value` і `shared_heap` однакова для всіх threads; але кожен thread має власний stack (8 МБ, `local` відрізняються на `0x801000`);
- порядок threads не гарантований: у `multiple_threads` було кілька різних порядків;
- `counter++` це три інструкції (`mov`, `add`, `mov`), тому два threads без синхронізації втрачають оновлення: `1114953` замість `2000000`, на 10M ітерацій помилка в кожному запуску;
- гонка проявляється нерегулярно (10 зі 100 запусків на 1M ітерацій), тому тестами її відсутність довести не можна;
- `mutex` забезпечує mutual exclusion і виправляє результат (5 із 5), але має ціну: lock на кожній ітерації в 10–25 разів повільніший, а широкий lock прибирає паралелізм;
- більше threads не означає швидше: 4 threads з mutex не швидші за 2, а без mutex помилок ще більше;
- deadlock виникає через circular wait (протилежний порядок lock); усі threads сплять у `futex_wait` і не споживають CPU; однаковий порядок блокувань його усуває;
- найкращий спосіб уникнути race condition це зменшити shared mutable state: `parallel_sum` дає правильний результат без жодного mutex і на великому N у ≈2,3 рази швидший за послідовну версію.

</details>
